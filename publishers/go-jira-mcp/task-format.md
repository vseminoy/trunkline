# Контракт издателя go-jira-mcp: формат markdown-задачи

Что должно быть в `.md`-файле, чтобы сервер `go-jira-mcp` смог создать из него задачу
в JIRA. Здесь только то, что **проверяет и разбирает код**: имена и типы полей,
правила размещения файлов, порядок заведения, поведение при ошибке.

Соглашений о том, **что писать** внутри этих полей — какой должна быть тема, из каких
блоков состоит тело, в какой нотации формулируются критерии приёмки — здесь нет и не
должно быть: это стандарты команды, и они живут в профиле стека
(слот `tasks.format_spec`, см. `profiles/README.md`). Профиль ссылается на этот файл,
а не пересказывает его.

Нарушение контракта — отказ в заведении задачи с ошибкой в отчёте. Нарушение соглашений
профиля код не заметит: это работа ревью.

---

## 1. Базовые правила

- **Один файл = одна задача.**
- Кодировка UTF-8, расширение `.md`.
- Файл состоит из двух частей:
  1. **YAML front-matter** — **обязательный** блок метаданных в начале файла,
     ограниченный строками `---`. Без него файл считается невалидным.
  2. **Тело** — всё, что после front-matter; идёт в `description` задачи как есть
     (plain text / wiki-markup).
- Обязательные поля front-matter: **`project`**, **`summary`**, **`ready`**,
  **`type`** (см. §3).

## 2. Размещение файлов: папка = эпик

Задачи лежат в папке, **имя которой совпадает с ключом эпика** в JIRA.
Эпик задачи определяется именем родительской папки — отдельно указывать его в
каждом файле не нужно.

```
<корень задач>/
├── PROJ-855/                  # эпик PROJ-855
│   ├── C1-fix-excel-export.md
│   ├── C2-add-csv-import.md
│   ├── C2-add-csv-import/   # папка задачи C2 (вложения, см. §3.3)
│   │   └── sample.csv
│   └── done/                # обработанные задачи этого эпика
└── DEMO-100/                 # эпик DEMO-100
    └── B1-refactor-auth.md
```

- Имя папки (`PROJ-855`, `DEMO-100`) — валидный ключ эпика JIRA.
- Эпик задаётся **только** именем папки; отдельного поля `epic` во front-matter нет.
- Подпапка `done/` и всё её содержимое (`*/done/**`) при сканировании
  **исключается** — обработанные задачи повторно не подхватываются.
- Где лежит корень задач — решает не этот файл: путь объявлен слотом `tasks.dir`
  профиля и передаётся серверу переменной `TASKS_DIR`.

### 2.1. Именование файлов и порядок заведения

Имя файла начинается с **буквенно-числового префикса** — буква + номер: `B1`,
`C1`, `C2`, `C3` и т.д. (`C1-fix-export.md`, `C2-add-import.md`).

Задачи заводятся **в порядке этого префикса**: сначала по букве (`A` < `B` < `C`…),
затем по числу по возрастанию (`C1` → `C2` → `C10`, число сравнивается как число,
а не как строка). Это и есть порядок создания: блокирующая задача должна иметь
префикс **раньше** зависимой, чтобы её ключ существовал к моменту связи (см. §3.2).

## 3. Поля front-matter

| Поле | Обяз. | Тип | Назначение | Если не задано |
|---|---|---|---|---|
| `project` | **да** | строка | Ключ JIRA-проекта задачи (напр. `MAS`) | файл невалиден |
| `summary` | **да** | строка | Тема (заголовок) задачи | файл невалиден |
| `ready` | **да** | bool | Готовность к заведению в JIRA (см. §3.1) | файл невалиден |
| `type` | **да** | строка | Тип задачи (`Task`, `Bug`, `Story`…) | файл невалиден |
| `labels` | нет | список строк | Метки задачи | без меток |
| `links` | нет | список строк | Ключи блокирующих задач (см. §3.2) | без связей |
| `attachments` | нет | список строк | Файлы-вложения из папки задачи (см. §3.3) | без вложений |
| `estimate` | нет | строка | Исходная оценка трудозатрат (Original Estimate), напр. `2d 4h` (см. §3.4) | без оценки |
| `status` | нет | строка | Статус задачи в workflow JIRA, напр. `Open`, `In Progress`, `In Review`, `Closed` (см. §3.5) | без статуса |

> Эпик берётся из имени папки (см. §2), приоритет всегда `Medium` — отдельных
> полей `epic` и `priority` во front-matter нет.

### 3.1. `ready` — гейт на заведение

- `ready: true` — задача готова, **заводим** её в JIRA.
- `ready: false` — над задачей ещё работают: **не заводим**, файл
  **пропускаем и не перемещаем** (остаётся на месте до следующего прогона).

### 3.2. `links` — блокирующие задачи

`links` — список **блокирующих** задач (в JIRA создаётся связь типа
**is blocked by**). Может быть пустым или отсутствовать. Каждый элемент даёт одну
связь `is blocked by`.

В `links` можно указывать значения двух видов:

| Вид | Формат | Пример | Когда использовать |
|---|---|---|---|
| **JIRA-ключ** | `БУКВЫ-ЧИСЛО` | `PROJ-900` | задача уже существует в JIRA |
| **Локальная ссылка** | префикс файла из этой же папки | `C1` | блокер заводится в этом же прогоне |

```yaml
links: [PROJ-900, C1]
```

Правила:

- Различение: значение вида `ABC-123` (буквы-дефис-число) — это **JIRA-ключ**;
  иначе — **локальная ссылка** (префикс файла, напр. `C1`).
- **Локальная ссылка** разрешается в JIRA-ключ автоматически. Блокер ищется:
  - среди задач, заведённых **в этом же прогоне** (его новый ключ запоминается), либо
  - в подпапке **`done/`** этой эпик-папки, если блокер завели в **прошлый**
    прогон (его `jira_key` уже записан в файле, который туда переехал).
- Локальная ссылка должна указывать на задачу с **меньшим** префиксом (она
  заводится раньше). Если блокер `ready: false` или не найден (ни среди новых,
  ни в `done/`) — зависимая задача **не создаётся** и попадает в отчёт с ошибкой.

### 3.3. `attachments` — файлы-вложения

Файлы хранятся в **папке задачи** — это подпапка рядом с `.md`, имя которой
совпадает с именем файла **без расширения**:

```
PROJ-855/
├── C2-fix-export.md
└── C2-fix-export/          # папка задачи C2
    ├── diagram.png
    └── specs/api.pdf
```

В `attachments` перечисляются пути к файлам **относительно папки задачи**:

```yaml
attachments:
  - diagram.png
  - specs/api.pdf
```

Правила:

- Каждый путь резолвится в `<папка_задачи>/<путь>`.
- Файлы загружаются в JIRA **после** создания задачи.
- **Строгая проверка**: если перечисленный файл не найден или превышает лимит
  размера вложения на инстансе — задача **не создаётся**, в отчёт пишется ошибка.
- При переезде задачи в `done/` её папка перемещается **вместе** с `.md`
  (`done/C2-fix-export.md` + `done/C2-fix-export/`) — бандл остаётся целым.
- Картинки, на которые ссылается тело (`![](...)`, см. §4.1), добавляются к
  вложениям **автоматически** — отдельно в `attachments` их перечислять не нужно.
  Поле `attachments` — для файлов, которые не показываются в тексте (csv, pdf,
  архивы и т.п.).

### 3.4. `estimate` — исходная оценка трудозатрат

`estimate` — исходная оценка времени на задачу (JIRA *Original Estimate*) в
формате JIRA: `2d 4h`, `30m`, `1w` и т.п. Поле необязательное.

- При выгрузке эпика (`pull_epic`) оно **заполняется автоматически** из поля
  *Original Estimate* скачиваемой задачи; если оценка в JIRA не задана — поле
  опускается.
- Для новых задач его можно указать вручную; пустое или отсутствующее значение
  означает «без оценки».

### 3.5. `status` — статус задачи в workflow

`status` — название статуса задачи в текущем workflow JIRA (поле `status.name`):
`Open`, `In Progress`, `In Review`, `Closed` и любые другие статусы, настроенные
в вашем процессе. Значение сохраняется дословно, как в JIRA.

- При выгрузке эпика (`pull_epic`) оно **заполняется автоматически** из статуса
  скачиваемой задачи.
- Поле доступно **только для чтения** — это зеркало статуса JIRA, при синхронизации
  обратно в JIRA оно не отправляется и статус задачи не меняет (переходы по
  workflow выполняются отдельными transition-операциями, не редактированием поля).

## 4. Тело документа

Тело уходит в `description` **как есть**. Из чего оно состоит — вопрос профиля;
код разбирает в нём ровно две вещи: картинки (§4.1) и разметку JIRA (§4.2).

### 4.1. Картинки в описании

Чтобы картинка **отрисовалась в описании** задачи, она вставляется в тело
обычным markdown-синтаксисом изображения, а файл кладётся в **папку задачи**
(см. §3.3):

```markdown
На скриншоте видно ошибку:

![Ошибка 500](error.png)
```

Что делает инструмент с такой ссылкой:

1. Берёт файл `error.png` из папки задачи (путь — относительно неё, как у
   `attachments`).
2. **Загружает его как вложение** к задаче — отдельно перечислять в `attachments`
   **не нужно**, картинки из тела добавляются автоматически.
3. **Переписывает** markdown-картинку в JIRA-wiki: `![alt](error.png)` → `!error.png!`,
   и JIRA отрисует вложение прямо в описании.

**Правила для составителя файла (важно для корректной вставки):**

- Картинка пишется **только** так: `![подпись](имя_файла)`. Подпись (`alt`)
  необязательна, в JIRA не переносится — служит для читаемости markdown.
- Внутри `()` — **имя файла относительно папки задачи** (`error.png` или
  `screens/step1.png`), **без** URL и без пробелов.
- **Имя файла должно быть уникальным в пределах задачи**: JIRA ссылается на
  вложение по имени (`!error.png!`), а не по пути. Два разных `step1.png` в разных
  подпапках задачи — конфликт, так нельзя.
- Поддерживаемые форматы — обычные растровые (`png`, `jpg`, `jpeg`, `gif`, `webp`).
- **Внешние ссылки** (`![](https://…/pic.png)`) картинками-вложениями не считаются
  и не загружаются — остаются обычной ссылкой в тексте.
- Если файла, на который ссылается картинка, нет в папке задачи (или превышен
  лимит размера) — действует **строгая проверка** (§3.3): задача не создаётся,
  ошибка в отчёт.

### 4.2. Разметка: JIRA wiki, не Markdown

Описание уходит в JIRA **как wiki-markup**. Markdown-разметка тела, кроме картинок
(§4.1), не преобразуется — что написано, то и уедет в описание.

Практическое следствие: **таблицы markdown в JIRA не отрисуются.** Таблицы
оформляются нативным синтаксисом JIRA:

| Элемент | Wiki-markup |
|---|---|
| Заголовок строки | `\|\| Колонка 1 \|\| Колонка 2 \|\|` |
| Строка данных | `\| значение 1 \| значение 2 \|` |
| Моноширинный текст в ячейке | `{{идентификатор}}` (двойные фигурные скобки) |
| Подзаголовок секции | `h3. Заголовок` |
| Цитата | `bq. Текст цитаты` |

```text
|| Колонка 1 || Колонка 2 ||
| значение 1 | значение 2 |
```

Правила:

- Разделитель markdown `|---|---|---|` **не используется** — в JIRA его нет.
- `{code:<язык>}` работает только для языков, которые поддерживает **ваш инстанс**
  JIRA. Язык, которого там нет, даёт ошибку вида *Unable to find source-code
  formatter for language: …* — для таблиц `{code:…}` не применять вовсе.

## 5. Поля, добавляемые автоматически

После успешного создания задачи сервер **дописывает** во front-matter (перед
переносом файла в `done/`):

| Поле | Назначение |
|---|---|
| `jira_key` | Ключ созданной задачи, напр. `PROJ-901` |
| `jira_url` | Прямая ссылка `<JIRA_URL>/browse/<jira_key>` |
| `jira_created_at` | Время создания, ISO-8601 |

Эти поля — точка входа для последующего редактирования: по `jira_key` всегда
известно, какую задачу обновлять. Файлы с уже заданным `jira_key` повторно не
обрабатываются (защита от дублей).

## 6. Минимальный валидный файл

Всё обязательное и ничего сверх него. Как наполнять тело — в спеке формата профиля.

```markdown
---
project: BR
summary: Починить экспорт в Excel
ready: true
type: Bug
---
Тело задачи. Уходит в description как есть.
```

После заведения файл переезжает в `<эпик>/done/` вместе со своей папкой задачи,
а во front-matter появляются `jira_key`, `jira_url`, `jira_created_at` (§5).
