# Оценка пайплайна: как мерять и как читать

Пайплайн производит артефакты — спеки, миграции, описания тестов, отчёты
кросс-проверки — и сам себя журналирует. Эта страница про то, **как периодически
снимать с него показания**, чтобы находить поломки процесса и дорабатывать его по
данным, а не по ощущениям.

Отдельная страница нужна потому, что здесь два разных вопроса, и их постоянно
путают:

| Вопрос | Ответ даёт | Модель вызывается |
|---|---|---|
| Правильно ли устроены сами инструкции? | линтеры репозитория | нет |
| Что пайплайн наделал на реальных задачах? | журнал прогонов + `trunkline token-cost` | да, уже вызвана |

Первый вопрос дешёвый и проверяется в CI. Второй требует, чтобы прогоны уже
случились, и именно он ловит содержательные ошибки.

---

## Часть 1. Проверки репозитория (перед коммитом, в CI)

Быстрые, детерминированные, без обращения к модели. Все возвращают код 1 при
ошибках.

```bash
# структура скиллов: frontmatter, name = каталог, мёртвые кросс-ссылки
node scripts/lint-own-skills.js

# маршрутизация: попадает ли скилл в top-k по промпту пользователя
node scripts/run-own-evals.js

# ссылки на файлы пайплайна во всех инструкциях
python3 scripts/lint-pipeline-paths.py

# граница ядро/профиль: ядро не знает имён из профиля
python3 scripts/lint-core-profile-boundary.py

# локализации не разъехались с английским источником
python3 scripts/lint-l10n.py

# машинные гейты
bash scripts/test-approval-gate.sh
bash scripts/test-trace-check.sh
bash scripts/test-review-check.sh
bash scripts/test-token-cost.sh
```

**Что это НЕ проверяет.** `run-own-evals.js` — лексическое приближение
маршрутизации (TF-IDF по `name`×2 + `description`, косинус), а не семантика.
Он ловит два класса реальных багов: описание без слов, которыми говорит
пользователь, и слишком широкое описание, перебивающее нужный скилл. Провал
почти всегда означает «исправь `description`», **а не «исправь кейс»** —
подкрутить промпт в JSON до зелёного значит выключить проверку.

Кейсы лежат в `evals/cases/<имя-скилла>.json`, имя файла обязано совпадать со
`skill_name`. Конкурентами при ранжировании выступают и 24 скилла из
`agent-skills` — в живой сессии агент выбирает из всех сразу.

## Часть 2. Оценка реальных прогонов

Здесь и находятся содержательные ошибки. Источник — журнал прогонов в **проекте,
который разрабатывали**, не в этом репозитории:

```
<проект>/.pipeline/workdir/metrics/pipeline.jsonl
```

Одна строка = одно событие, append-only, не коммитится (мержится конфликтом
всегда, потому что все пишут в один конец).

### Когда запускать

- **Каждые 10 срезов** — так предписывает `core/developer/references/pipeline-evals.md`,
  и главный агент делает это сам.
- **По запросу** — скажите агенту «pipeline report».
- **Обязательно после смены маршрута, профиля или модели.** Это ровно те три
  вещи, которые ломают сравнение с прошлыми замерами, и знать об этом надо до
  того, как накопится статистика.
- **Руками — когда что-то ощущается неправильным.** Три отменённых подряд шага
  выглядят в чате как три мелких решения, а в журнале как закономерность.

Меньше 5 срезов — данных нет, есть анекдоты. Не режьте шаги по одному
наблюдению.

### Шаг 1. Что вообще прогнано

```bash
cd <проект>
python3 - <<'PY'
import json, collections
rows = [json.loads(l) for l in open('.pipeline/workdir/metrics/pipeline.jsonl') if l.strip()]
sl = collections.OrderedDict()
for r in rows: sl.setdefault(r.get('slice'), []).append(r)
for s, rs in sl.items():
    ev = collections.Counter(r.get('event') for r in rs)
    print(f'{s}  task={rs[0].get("task")}  {len(rs)} событий  {rs[0]["ts"][:16]}')
    print('   ', dict(ev))
PY
```

### Шаг 2. Шесть вопросов методики

Полный список — в `core/developer/references/pipeline-evals.md`. Практически они
снимаются так:

```bash
# 1. какие шаги находят дефекты
jq -r 'select(.event=="review" or .event=="security") |
  "\(.slice[-6:]) шаг \(.step) cs=\(.changeset) crit=\(.critical // 0) high=\(.high // 0) imp=\(.important // 0)"' \
  .pipeline/workdir/metrics/pipeline.jsonl

# 1b. кросс-проверка 7a — падавшие прогоны видны по rollback_to и lost
jq -r 'select(.event=="consistency") |
  "\(.slice[-6:]) cs=\(.changeset) gaps=\(.gaps) mism=\(.mismatches) lost=\(.lost // "—") trace=\(.trace_check) \(.rollback_to // "")"' \
  .pipeline/workdir/metrics/pipeline.jsonl

# 2. откаты и их причины
jq -r 'select(.event=="rollback") | "\(.slice[-6:]) \(.step) → \(.rollback_to): \(.reason)"' \
  .pipeline/workdir/metrics/pipeline.jsonl

# 3. пропущенные шаги — самый недооценённый сигнал, см. ниже
jq -r 'select(.event=="skipped") | "\(.slice[-6:]) шаг \(.step): \(.reason)"' \
  .pipeline/workdir/metrics/pipeline.jsonl

# 4. дельта-механика: окупается ли база знаний
jq -r 'select(.event=="delta_context") |
  "\(.slice[-6:]) reused=\(.reused_modules) rebuilt=\(.rebuilt_modules) stale=\(.stale)"' \
  .pipeline/workdir/metrics/pipeline.jsonl

# 5. стоимость прогона в подтверждениях и минутах
jq -r 'select(.event=="done") |
  "\(.slice[-6:]) подтверждений=\(.confirmations) откатов=\(.rollbacks) минут=\(.duration_min)"' \
  .pipeline/workdir/metrics/pipeline.jsonl
```

### Шаг 3. Деньги

```bash
trunkline token-cost --slice 260818200645     # один прогон, привязка через журнал
trunkline token-cost --session current        # текущая сессия
trunkline token-cost --all --format md        # всё, что проект стоил
```

В шапке отчёта смотрите на строку привязки: `bound by session_id from the journal
— exact` означает, что цифра относится к этому прогону. `wall-clock` означает,
что `session_id` в журнале не было и посчитано всё, что проект делал в окне
`start`→`done` — это верхняя оценка, а не стоимость прогона.

**Читайте доллары, а не токены.** Кэш-чтение обычно даёт около 97% токенов при
десятой доле цены за токен, поэтому любая единая цифра «токенов» доминируется
самым дешёвым компонентом и ничего не говорит.

## Как читать результат

### Шаг ничего не находит — три разных случая

Это главная ловушка, и различать их обязательно:

1. **Шаг действительно ceremony** — прогоняется, смотрит, не находит. Кандидат на
   вынос из маршрута.
2. **Шаг находит, но находки не доезжают до журнала.** Проверьте, есть ли рядом
   `rollback`, причина которого описывает находку этого шага. Если есть —
   сломана инструментовка, а не шаг. Ровно это случилось с 7a: он ловил
   потерянные требования, а событие писалось только после починки и перезапуска,
   когда счётчики уже обнулены.
3. **У шага нет события с находками в схеме вовсе** (11, 12, 15, 17). Они не
   «находят», они правят. Прежде чем что-то решать про такой шаг, надо понять,
   каким событием его польза вообще выражается — иначе отсутствие данных
   прочитается как отсутствие пользы.

**Никогда не выносите шаг из маршрута по одному только пустому счётчику.**
Сначала исключите случаи 2 и 3.

### Повторяющийся `skipped` — это предложение изменить маршрут

Одна отмена — решение по обстоятельствам. Три подряд с одинаковой причиной —
закономерность, которую надо перенести в маршрут. Читайте не факт пропуска, а
**текст `reason`**: если у трёх отмен общая формулировка вроде «новых веток кода
нет», у вас есть готовое условие для правила.

### Откаты

Ожидаемые точки — `7a → 5/6/7` и `9/10 → 8`. Один-два за срез — норма, так
пайплайн и работает. Систематический `7a → 2` означает, что правила регулярно не
доезжают до спеки, и чинить надо шаг 2, а не 7a.

### Отчёт — это предложение, а не изменение

Так записано в `pipeline-evals.md`, и это не формальность: сокращение маршрута —
решение человека. Отчёт называет кандидатов, аргументы к ним и цену.

## Гигиена журнала

Данные врут тише, чем ломаются гейты, поэтому проверяйте сам журнал:

- **`done` есть у каждого закончившегося прогона.** Прогон без `done` считается
  незавершённым (`core/developer/ENFORCEMENT.md`), и в статистику стоимости не
  попадает.
- **Поля `done` заполнены** — `confirmations`, `rollbacks`, `duration_min`.
  Пустые поля выглядят как записанное событие, но вопрос «что стоит чейнджсет» на
  таком срезе не отвечается.
- **`session_id` есть в `start`** — без него `trunkline token-cost` переходит на
  `wall-clock` и завышает.
- **`changeset` есть у всех событий внутри цикла** — шаги 5, 6, 7, 7a, 8, 9+10,
  11, 12, 15, 16, 18 идут по разу на чейнджсет, и событие без номера говорит,
  какому прогону оно принадлежит, но не какому куску работы.

Быстрая проверка:

```bash
jq -r 'select(.event=="done") |
  select(.confirmations == null or .duration_min == null) |
  "неполный done: \(.slice)"' .pipeline/workdir/metrics/pipeline.jsonl

jq -r 'select(.event=="start") | select(.session_id == null) |
  "start без session_id: \(.slice)"' .pipeline/workdir/metrics/pipeline.jsonl

# событие из цикла чейнджсетов без номера чейнджсета.
# Фильтр по шагу обязателен: 17 и 19 идут раз на прогон, у них changeset
# отсутствует законно, и проверка без фильтра даёт ложные срабатывания.
jq -r '["5","6","7","7a","8","9","10","9-10","11","12","15","16","18"] as $loop |
  select(.changeset == null) | select((.step|tostring) as $s | $loop | index($s)) |
  "\(.event) без changeset: \(.slice) шаг \(.step)"' .pipeline/workdir/metrics/pipeline.jsonl
```

**`consistency` от шага 17 — не то же самое, что от 7a.** Шаг 7a сверяет один
чейнджсет, шаг 17 при подготовке к сдаче сверяет правило→код по всей задаче.
События выглядят одинаково и различаются только полем `step`, поэтому при подсчёте
результативности 7a фильтруйте по нему — иначе прогон с тремя чейнджсетами даст
четыре события 7a и одно чужое, и среднее поедет.

## Чего пока нет

Уровня «прогнать пайплайн на эталонной задаче и померять результат» в
репозитории **нет**. Существующие проверки — это уровни 1 и 2:

| Уровень | Что проверяет | Чем | Модель |
|---|---|---|---|
| 1. Структурный | frontmatter, ссылки, границы | линтеры | нет |
| 2. Trigger & routing | попадает ли скилл в top-k | `run-own-evals.js` | нет |
| **3. Прогон пайплайна** | **покрытие правил, токены, откаты** | **отсутствует** | **да** |

Формат `evals/cases/*.json` под уровень 3 не расширяется: в нём только
`trigger.positive/negative` для лексического ранжирования, нет ни прогона модели,
ни доступа к `.pipeline/workdir/metrics/`, ни понятия «задача». Нужен свой каталог
(напрашивается `evals/pipeline/`) со своим раннером. Набросок первого
эксперимента — в `IDEAS.md`, раздел «Компактность артефактов».

До тех пор оценка уровня 3 — ручная процедура с этой страницы, и её ценность
целиком зависит от того, что журнал заполняется честно.
