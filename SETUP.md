# Подключение trunkline к проекту

Установка — одна команда. Дальше на этой странице: что она сделала, какие флаги вы
осознанно выбираете и что чаще всего идёт не так. Один раз на проект, дальше — только
запуск.

Термины, которые встречаются постоянно:

| Термин | Что это |
|---|---|
| **проект** | ваш код, из которого вы запускаете агента (текущая рабочая директория) |
| **профиль** | стек + чьи-то гайдлайны: `.trunkline/profiles/<имя>/profile.yaml` |
| **база знаний** | всё, что хранится навсегда: ADR, AS-IS модулей, история слайсов. Корень — `.pipeline/knowledge/`, внутри каталог на проект |

Всё, что настраивается, настраивается **в проекте**: `trunkline` вендорит туда ядро,
профиль и нужную часть `agent-skills`, поэтому проект самодостаточен и версионирован.

---

## Шаг 1. Поставить CLI

```bash
go install github.com/vseminoy/trunkline/cmd/trunkline@latest
# или из клона репозитория (соберёт бинарь в свою папку и предложит
# добавить её в PATH; на Windows — scripts/install.ps1):
make install
```

Проверка: `trunkline version`. Обратное действие — `make uninstall`.

## Шаг 2. Выбрать профиль

```bash
trunkline profile list
```

| Профиль | Стек | Чьи гайдлайны |
|---|---|---|
| `oss-py-fastapi` | Python, FastAPI + Pydantic v2, aiosql, Alembic, PostgreSQL+PostGIS | общепринятые практики экосистемы (`oss-`) |
| `example-stack` | шаблон — скопировать под свой стек и заполнить слоты | — |

Имя профиля начинается с организации: гайдлайны — это **чьи-то** стандарты. Ваш стек
совпадает, а правила по типам, авторизации и миграциям — свои → нужен свой профиль,
см. `profiles/README.md`. Копировать чужой и править его «немножко под себя» — худший
вариант: расхождение всплывёт на шаге 7a в виде необъяснимых сверок.

Профиль **обязателен**. Не объявлен — агент останавливается и спрашивает; угадывать
стек по коду ему запрещено, потому что неверный профиль молча отключает часть сверок.

## Шаг 3. Установка

Из корня разрабатываемого проекта:

```bash
trunkline init --profile oss-py-fastapi
```

Что произойдёт:

```
.trunkline/            ← ядро, профиль, agent-skills (вендорится, коммитится)
├── core/
├── profiles/<имя>/
├── agent-skills/
└── AGENTS.md          ← нейтральная точка входа: работает в любом агенте
.claude/
├── commands/trunkline-dev.md   ← слэш-команда Claude Code
├── commands/trunkline-quick.md ← короткие правки без пайплайна
├── hooks/pre-commit-gate.sh    ← гейт сборки и линтера
└── settings.json               ← регистрация гейта (мерджится, не перезаписывается)
.pipeline/             ← база знаний (коммитится); журнал, правила и отчёты прогона — в .gitignore
AGENTS.md              ← добавляется блок ## Pipeline flags, если его не было
```

Полезные флаги:

| Флаг | Зачем |
|---|---|
| `--language ru` | локализация ядра (по умолчанию `en`); `ru` намеренно частичная — см. шаг 4a; список — `trunkline init --help` |
| `--gate=claude` (умолчание) | гейт как `PreToolUse`-хук Claude Code |
| `--gate=git` | гейт как `.git/hooks/pre-commit` — работает с любым агентом |
| `--gate=none` | без машинного гейта (осознанная дыра в enforcement) |
| `--knowledge`, `--project`, `--metrics` | сразу задать пути, имя проекта или `none` |
| `--dry-run` | показать, что изменится, ничего не записывая |

`init` безопасно перезапускать: существующий блок флагов не переписывается никогда,
а файлы, которые вы правили руками, `update` сохраняет и перечисляет. Файл, которого
нет в `.trunkline/state.yaml`, тоже не трогается — он помечается `kept (not ours)`:
записи нет, значит, положили его не мы. Перезаписать такой файл — `--force`.

`--gate=git` откажется ставить хук, если в репозитории задан `core.hooksPath`
(husky, lefthook): туда хук ставить нельзя — он затрёт чужой, а в `.git/hooks/`
он бы просто никогда не запустился. Что делать, сказано в тексте отказа.

## Шаг 4. Проверить блок флагов в `AGENTS.md`

Блок лежит в `AGENTS.md`, а не в файле правил конкретного хоста: флаги настраивают
пайплайн, а пайплайн не привязан к одной LLM. `AGENTS.md` читают и Claude Code,
и Codex, и Cursor.

`init` пишет блок с умолчаниями. Полный список:

```markdown
## Pipeline flags
- profile: oss-py-fastapi                      # обязателен
- language: ru                                 # язык промптов и артефактов; en — исходник
- knowledge: .pipeline/knowledge               # корень базы; может держать несколько проектов
- project: <имя-каталога-проекта>              # каталог этого репозитория внутри неё
- metrics: .pipeline/workdir/metrics/pipeline.jsonl    # журнал прогонов
- secrets_in_code: false                       # секреты в исходниках — норма проекта
- long_lived_branches: false                   # ветки живут дольше 3 дней
- staged_rollout: false                        # поэтапная раскатка критических путей
- sound: true                                  # звук, когда прогон остановился и ждёт человека
# - rps: 2000                                # ориентир нагрузки (шаги 12, 16)
# - host: cursor                             # claude-code (по умолчанию) | cursor | codex | generic
```

| Флаг | Значения | Не задан |
|---|---|---|
| `profile` | имя папки в `.trunkline/profiles/` | **остановка и вопрос** |
| `language` | `en` или локализация из `core/l10n/` | `en` |
| `knowledge` | корень базы: путь, внешний путь или `none` | `.pipeline/knowledge/` |
| `project` | каталог проекта внутри корня | имя каталога, в котором запускался `init` |
| — | рабочие файлы прогона, чистятся по возрасту | `.pipeline/workdir/` |
| `metrics` | путь или `none` | `.pipeline/workdir/metrics/pipeline.jsonl` |
| `secrets_in_code` | `true` / `false` | `false` (строго) |
| `rps` | число | **спросит**, а не додумает |
| `long_lived_branches` | `true` / `false` | `false` (строго) |
| `staged_rollout` | `true` / `false` | `false` |
| `sound` | `true` / `false` | `true` (звук включён) |
| `host` | `claude-code` / `cursor` / `codex` / `generic` | `claude-code` (ничего не деградирует) |

Правило одно: **не задан → строгое поведение**. Исключение — `sound`: он ничего не проверяет,
а только зовёт человека к терминалу, поэтому незаданный флаг означает включённый звук.
 Флаг — это способ осознанно отключить
проверку, а не способ про неё забыть. `rps` намеренно закомментирован: незаданный `rps`
заставляет агента спросить, а не выдумать цель по нагрузке. `host` закомментирован по той же
причине с другим умолчанием: пустой означает `claude-code` — единственный хост, на котором
ничего не деградирует. Любое другое значение обязывает агента прочитать
`.trunkline/core/ORCHESTRATION.md` на старте и назвать, каких возможностей нет и чего это
стоит (параллельное ревью шага 9+10, машинный гейт коммита, кэш документации). Хост
объявляется, а не определяется: угаданная возможность отключает проверку молча. Все флаги объявляются вслух
на шаге 0, чтобы отключённый гейт был виден вам, а не только агенту.

## Шаг 4a. Язык

Ядро написано по-английски; `language` выбирает локализацию, которая накладывается
поверх него (`core/l10n/<язык>/`). Непереведённый файл берётся английским — частичная
локализация работает, а не ломает маршрут.

```bash
trunkline init --profile oss-py-fastapi --language ru
```

Что важно понимать:

- **Язык выбирается один раз, при установке.** `update` читает флаг и держит его:
  молча вернуть локализованный проект на английский — единственное, чего он не сделает.
- **Язык промпта и язык артефактов — не одно и то же.** Правило в ядре сильнее флага:
  агент пишет спеки, тесты, базу знаний и коммиты на том языке, на котором проект уже
  ведёт код и документацию, и не переводит их из-за языка промпта. Русские артефакты
  получаются и на английском промпте — переводить ядро ради них не нужно.
- **`ru` покрывает малую часть ядра, и так задумано.** Переведено то, что либо копируется
  в артефакт дословно (шаблон базы знаний, эталон `tests_readme.md`), либо завязано на
  форму русского языка (EARS-нотация `КОГДА`/`ЕСЛИ … ТО` в аналитическом пайплайне).
  Пайплайн разработчика целиком английский: это процедура, она берётся фолбэком и всё
  равно пишет артефакты по-русски. Обоснование — `core/l10n/README.md`, раздел
  «What earns a translation».
- **`trunkline doctor`** покажет выбранный язык, а расхождения перевода с исходником ловит
  `python3 scripts/lint-l10n.py` в репозитории пайплайна.

Своего языка нет — `core/l10n/README.md`, там же правила: что вообще имеет смысл
переводить, и что переводится проза, но не протокол (идентификаторы, имена флагов и
слотов, идентификаторы правил `R-007-2`, маркеры `[STOP]`, `ADDED`/`MODIFIED` — они английские
на любом языке).

## Шаг 5. Решить, какую базу знаний вести

Флаг `knowledge` объявляется ровно так же явно, как профиль, и по той же причине:
из него агент узнаёт, откуда брать AS-IS, а не собирать заново.

**`knowledge` — это корень базы, а не каталог одного проекта.** База может быть общей
на всю компанию: несколько сервисов указывают на один путь и различаются только
флагом `project`.

```
<knowledge>/                # флаг knowledge — корень, возможно общий на компанию
├── INDEX.md                # оглавление по ВСЕМ проектам базы
├── <project>/              # флаг project — этот репозиторий
│   ├── adr/                # необратимые решения и их цена (шаг 15)
│   ├── modules/            # AS-IS каждого модуля (шаг 20, перезаписывается)
│   └── slices/             # история изменений, запись на прогон (только дозапись)
└── <другой-сервис>/        # другой репозиторий, тот же корень
```

Без второго флага два сервиса с общим корнем писали бы каждый свой
`modules/payments.md` в одно место, и второй прогон молча затёр бы первый.
`INDEX.md` остаётся в корне намеренно: «описан ли этот модуль хоть у кого-то из наших
сервисов» — вопрос, ради которого общую базу и заводят, и изнутри одного каталога
на него не ответить.

Умолчание `project` — имя каталога, в котором запускался `trunkline init`. Задать явно:
`trunkline init --project billing` или строкой в `AGENTS.md`.

Всё остальное, что пишет пайплайн, — реестр правил, сверка шага 7a, отчёты ревью и
журнал — лежит в `.pipeline/workdir/`, живёт один прогон и не коммитится. Одна строка
в `.gitignore`:

```gitignore
/.pipeline/workdir/
```

Каталог не чистится сам: раз в неделю или из шага 20 запускается
`.trunkline/core/developer/scripts/workdir-clean.sh` — он удаляет файлы старше семи
дней, не трогая журнал и не трогая прогоны, у которых ещё нет строки `done`.

```markdown
- knowledge: .pipeline/knowledge              # своя база в этом репозитории (умолчание)
- knowledge: ../platform/.pipeline/knowledge  # общая база нескольких сервисов
- knowledge: none                             # не вести
```

Что происходит при каждом варианте:

- **свой путь** — шаг 1 читает базу первым действием, шаг 20 дописывает слайс. Вторая
  задача по тому же модулю обходится заметно дешевле первой.
- **внешний путь** — так подключается монорепозиторий или связка сервисов с общим
  доменом. Писатель по-прежнему один: шаг 20 запущенного пайплайна. Если в базу пишут
  из нескольких репозиториев, договоритесь о префиксах имён модулей — иначе `payments.md`
  будет означать два разных модуля.
- **`none`** — база не ведётся. Это рабочий режим для разового проекта, но агент обязан
  объявить его на шаге 0: прогон без базы выглядит так же, а стоит контекста вдвое дороже.

База знаний **коммитится вместе с кодом**. Она описывает состояние кода на конкретный
коммит; в `.gitignore` ей не место — `trunkline doctor` проверяет обе стороны: что база
не спрятана и что `workdir/` не уезжает в общую историю.

Структура и формат — `.trunkline/core/skills/project-knowledge/SKILL.md`. Заводить
руками ничего не нужно: на первом прогоне шаг 20 создаст структуру сам.

## Шаг 6. Проверить настройку

```bash
trunkline doctor
```

Проверяет всё разом: установлен ли пайплайн, не разошлись ли версии, есть ли непринятые
миграции, объявлен ли профиль и установлен ли он, на месте ли `required_project_files`
профиля, разрешаются ли роли гайдлайнов, существует ли база знаний, не попала ли она
в `.gitignore`, привязан ли гейт коммита к реальному триггеру, есть ли точка входа
и какие вендоренные файлы вы правили локально.

Ненулевой код возврата = что-то сломает прогон. `warn` — работать будет, но с
отключённой частью.

## Шаг 7. Первый прогон

```
/trunkline-dev не сохраняется расписание автоплатежа, падает на пустом теле
```

Агент обязан на старте объявить: тип задачи, профиль и его версию, базу знаний, флаги,
маршрут шагов. Если чего-то из этого списка в объявлении нет — настройка не подхватилась,
и дальше идти не стоит.

Дальше — `[STOP]` на каждом шаге. «продолжай» = перейти к следующему шагу, не «пройди
всё до конца».

В агенте без слэш-команд запуск другой: «следуй `.trunkline/AGENTS.md`». Что именно
деградирует в таком хосте и что с этим делать — `.trunkline/core/ORCHESTRATION.md`.

## Обновление

```bash
trunkline update            # ядро и профили до версий текущего бинаря
trunkline update --dry-run  # посмотреть, что изменится
```

`update` прогоняет миграции формата, сохраняет файлы, которые вы правили руками
(и перечисляет их), и удаляет то, что больше не поставляется. `--force` перезаписывает
локальные правки.

## Проверочный список

```
[ ] trunkline version печатает версию
[ ] trunkline doctor — ноль FAIL
[ ] в AGENTS.md проекта есть блок ## Pipeline flags
[ ] profile указан и такая папка есть в .trunkline/profiles/
[ ] knowledge осознанно выбран (или сознательно оставлен по умолчанию)
[ ] project назван так, как проект зовут в компании — если база общая, это имя увидят все
[ ] файлы из required_project_files профиля существуют
[ ] pre-commit-гейт установлен либо явно решено обойтись без него (--gate=none)
[ ] .trunkline/ и .pipeline/ закоммичены и не попали в .gitignore
```

## Что чаще всего идёт не так

| Симптом | Причина |
|---|---|
| Агент спрашивает профиль на каждом запуске | блок флагов не в `AGENTS.md` проекта, а в другом файле или в другом репозитории |
| Шаг 1 каждый раз собирает AS-IS с нуля | `knowledge: none`, либо путь указывает в несуществующий каталог |
| Шаг 8 пишет руками то, что должен генерировать | профиль указан неверный — в его `stack` нет вашего кодогенератора |
| Сверки шага 7a «не применимо» на всём подряд | в профиле не заполнены `guidelines.roles` |
| Коммит проходит при падающем билде | гейт не привязан к триггеру или потерял бит `+x`: `doctor` теперь показывает оба случая как `FAIL`; чинится повторным `trunkline init --gate=claude` или `--gate=git` |
| `.pipeline/` пропал у коллеги | попал в `.gitignore` — база знаний должна коммититься |
| `update` не подтянул правку ядра | файл правился локально и был сохранён; `doctor` перечисляет такие файлы |

## Настройка своего стека

Если готового профиля нет — `profiles/README.md`. Коротко: скопировать манифест,
заполнить слоты, положить гайдлайны, написать надстройки шагов **только там, где стек
реально что-то добавляет**, и прогнать:

```bash
python3 scripts/lint-core-profile-boundary.py
```

Линтер проверит, что все слоты, на которые ссылается ядро, в вашем манифесте объявлены,
а пути существуют. Одну живую задачу по полному маршруту `feature` после этого всё равно
надо прогнать руками: линтер видит структуру, но не видит, осталось ли в шаге достаточно
смысла.
