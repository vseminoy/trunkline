# Step 19. CI agent `[CONDITIONAL]`

**Skills:** `agent-skills/skills/ci-cd-and-automation/SKILL.md`

## When it runs

**On `config/ci` the step is the task**, and it is not conditional there: the route is
`1 → 19 → 18 → 20`, the CI files are what the run changes, and step 18 commits them.

**On `feature` it is conditional, and the condition is that the delivery changed what CI has to
do.** At least one of:

- a command in the profile's `commands.*` changed, or the delivery added work that no command runs
  yet (a new generator step, a new lint target);
- a test the current pipeline cannot run as it stands — an integration test needing a service, a
  fixture, a longer timeout;
- a migration the deploy has to apply, or a new environment variable the pipeline must carry;
- a new dependency of the build itself: a toolchain version, a code generator, a base image.

**"This project has no CI" is not on that list.** A missing pipeline is a decision about the
project, not a rider on the task in hand — building one costs more than most features and touches
files the task never named (prohibition 5, scope discipline). Say it once in the report and offer to
take it as its own `config/ci` task. The same answer applies to a CI that is merely slow or badly
ordered: the "Faster is Safer" work below is worth doing, and it is worth doing as its own task.

**Ask before running it, and record the answer.** `[CONDITIONAL]` means the user decides; the list
above decides only whether to offer. If the step does not apply, say so in one line with the reason
and write `skipped` to the journal — "not applicable" and "nobody looked" are different statements
about a delivery, and only the journal keeps them apart.

## On `feature` this step writes nothing

It runs **after** the last step 18 (the route is `… → 17 → 19? → 20`), and only steps 18 and 20
commit — see "The commit boundary is also the recovery boundary" in the core. Step 20's commit
carries the knowledge base and nothing else, so a CI file edited here would sit uncommitted at the
end of the run, or be swept into a commit that is not about it. Neither is acceptable.

So on `feature` the step **produces a proposal, not an edit**: what CI must gain, why the delivery
requires it, and the concrete diff to make — handed over as a `config/ci` task, which has step 18
after step 19 for exactly this reason. On `config/ci` the edits are the work and are written
normally.

The one thing that is done rather than proposed, on either route, is the check below that the
machine gate exists — it changes the project's `.claude/settings.json` or `.git/hooks/`, neither of
which is committed, and it needs the user's explicit consent anyway.

Apply the "Faster is Safer" principle and the deployment strategies from the skill.

**Shift Left:** a problem caught in lint costs minutes. In prod it costs hours. Put the gates as
early as possible.

**Mandatory gate order:**
```
Lint → Type Check → Unit Tests → Build → Integration Tests → Security Audit
```

Optimise the dependency cache if a run takes more than 5 minutes.
If there is no CI → propose a minimal pipeline for the profile's language, as the content of the
`config/ci` task named above; agree it before creating anything, and create it there rather than
here.

**Machine enforcement instead of textual (see `core/developer/ENFORCEMENT.md`):** check that the
pipeline's local gates are moved into hooks or the Makefile rather than resting on the agent's
obedience — above all the profile's `commands.lint` and `commands.build` before a commit. If there
is no hook — offer to install one.
