# Сценарий B: ревью, дооценка и дополнение задач

## Overview

Когда декомпозиция уже частично сделана (своя или чужая), задача аналитика — не переписать её
заново, а **привести в порядок**: проинвентаризировать существующие задачи, проверить каждую
на соответствие спеке формата и на полноту (Проблема/Решение/Как тестировать), **проставить
оценку там, где её нет**, найти **пробелы в покрытии** и **дописать недостающие** задачи,
затем пересобрать порядок по зависимостям. Режим — только чтение по коду; файлы задач
изменяются/добавляются только с согласия пользователя.

## When to Use

- В папке эпика уже лежат задачи, и их надо посмотреть/оценить/дополнить.
- Часть задач без оценки, часть не по формату, есть подозрение на пропуски в покрытии.
- Пришла чужая декомпозиция на ревью.

**When NOT to use:** задач нет вообще → `decompose-from-scratch`; задачи в порядке, но
есть нерешённые открытые вопросы/блокеры → `resolve-open-questions`.

## Откуда берутся задачи

Входа два, и сценарий работает от любого:

- **`<tasks.dir>/<ЭПИК>/`** — задачи, живущие в репозитории: написанные прошлым прогоном
  сценария A или человеком.
- **`<tasks.dir>/<ЭПИК>/in_jira/`** — зеркала задач, уже заведённых в трекере; их скачивает
  операция издателя `operations.pull`. Именно это делает «на ревью пришла чужая декомпозиция»
  маршрутом, а не перепечатыванием: источник — трекер, а в front-matter зеркал стоит ключ задачи,
  поэтому последующая публикация **обновит** эти задачи, а не создаст дубли.

Оба пути берутся из манифеста — разрешить `tasks.dir` и дописать ключ эпика; буквальный `tasks/`
не предполагать. Если `in_jira/` нет, а эпик в трекере явно есть — сказать это и предложить
пользователю `operations.pull`, ровно так же, как предлагается публикация: операцию запускает
пользователь. Если профиль не объявляет `operations.pull`, этого входа в проекте просто нет —
сказать одной строкой, а не выдумывать способ забрать задачи.

## Process

В начале — загрузить/создать состояние (`analysis-state`, сценарий = B).

### 1. Инвентаризация `[STOP]`
Прочитать все `.md`-задачи в папке эпика (исключая `done/`), а также зеркала в `in_jira/`, если они есть. Для каждой собрать строку
таблицы состояния: префикс, файл, summary, оценка, `ready`, `links`. Не угадывать содержимое —
читать файлы.

### 2. Проверка формата `[STOP]`
Прочитать спеку формата (`tasks.format_spec` профиля). Для каждой задачи проверить:
- валидный YAML front-matter, обязательные поля `project`/`summary`/`ready`/`type`;
- тело из трёх блоков: **Проблема → Решение → Как тестировать**;
- `summary` отражает бизнес-эффект; `links` указывают на существующие/локальные блокеры;
- расположение в папке-эпике и корректный префикс (`A`<`B`<`C`, число как число).

Классифицировать статус анализа каждой: `готова` / `неполная` / `не по формату` /
`нужна оценка` / `нужен пересмотр` / `дубликат`.

### 3. Анализ покрытия (поиск пропусков) `[STOP]`
Свериться с требованиями, чтобы найти **недостающие** задачи. Лёгкий прогон Импакт-Аналитика
из `decompose-from-scratch` (скил `deprecation-and-migration`): какие слои/контракты/миграции
должны быть затронуты по TO-BE, и какие из них **не покрыты** ни одной существующей задачей.
Типичные пропуски: миграция без запросов к БД, хендлер без обновления контракта, фича без тестов,
отсутствует фундаментная задача (схема/контракт), нет обратной совместимости.

Собственный взгляд на чужую декомпозицию быстро становится соучастником: прогнать **цикл сомнения**
(скил `doubt-driven-development`). ARTEFACT — набор существующих задач, CONTRACT — спека формата
плюс полнота покрытия относительно описания эпика; ревьюеру передаётся **без** своих выводов.
Вопрос: какой сценарий из описания не покрыт ни одной задачей.

**Выход:** список пробелов → новые задачи (черновики).

### 4. Дооценка `[STOP]`
Проставить оценку каждой задаче **без оценки** по таблице ниже (тот же критерий, что в
`decompose-from-scratch`). Любую задачу с оценкой **> 24 ч** вернуть к дроблению (как в
Декомпозере). Оценки — в сводный отчёт, не в файлы задач.

### 5. Дописать недостающие и пересобрать порядок `[STOP]`
Оформить новые задачи строго по спеке формата, присвоив **следующие свободные префиксы**
так, чтобы блокеры шли раньше зависимых. Пересчитать граф зависимостей и `links` у затронутых
задач. **До сохранения/правок** спросить: подтверждение правок существующих файлов, поля
front-matter новых, эпик/папку (если не из состояния). **Выход:** обновлённый набор файлов +
сводный отчёт + состояние (с открытыми вопросами, найденными при ревью).

## Оценка

Таблица размеров и всё, что к ней прилагается, — коэффициенты затухания по типу требования и слою,
множитель для тонкого прокси, плоская ставка на миграции, отдельная строка на снос старого пути —
лежат у Оценщика, `core/analytic/steps/a05-estimator.md`. Пользоваться ими оттуда.

Здесь они намеренно не пересказаны: копия таблицы размеров без правил затухания завышает оценку
многотребовательной задачи примерно вдвое — ровно та ошибка, о которой предупреждает шаг 5, — и
дробит задачи, которые были здоровыми.

## Чек-лист ревью одной задачи

- [ ] Front-matter валиден, обязательные поля на месте.
- [ ] Тело: Проблема / Решение / Как тестировать — все три, не пустые.
- [ ] `summary` про бизнес-эффект, не про реализацию.
- [ ] `links` корректны (блокер существует и имеет меньший префикс или это JIRA-ключ).
- [ ] Оценка проставлена и ≤ 24 ч.
- [ ] Задача — законченный вертикальный слайс, не «кусок слоя».
- [ ] Нет дублирования с другой задачей.

## Common Rationalizations

| Рационализация | Реальность |
|---|---|
| «Перепишу всё заново — так быстрее» | Это сценарий A. Здесь надо сохранить уже сделанное и достроить, а не выкинуть. |
| «Оценю на глаз, не читая файл» | Оценка без чтения тела и затронутых слоёв — фикция. Читать. |
| «Покрытие выглядит полным» | Пробелы не видны без сверки с TO-BE по слоям. Прогнать анализ покрытия явно. |
| «Поправлю чужие файлы молча» | Правки существующих задач — только с согласия пользователя. |

## Red Flags

- Инвентаризация по именам файлов без чтения их содержимого.
- Новые задачи с префиксами, нарушающими порядок блокеров.
- Дооценка без проверки потолка 24 ч.
- Найденные пробелы не превращены ни в задачи, ни в открытые вопросы.
- Состояние не обновлён статусами анализа задач.

## Verification

- [ ] Все существующие задачи прочитаны и классифицированы в таблице состояния.
- [ ] Каждая проверена по спеке формата; несоответствия зафиксированы.
- [ ] Все задачи без оценки дооценены; ни одна не > 24 ч.
- [ ] Пробелы покрытия закрыты новыми задачами или внесены в открытые вопросы.
- [ ] Порядок (префиксы) и `links` пересобраны по графу зависимостей.
- [ ] Правки/добавления согласованы до сохранения; состояние и отчёт обновлены.
