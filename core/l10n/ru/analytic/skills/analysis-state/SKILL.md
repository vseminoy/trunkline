# Состояние анализа

## Overview

Состояние анализа — единственный персистентный носитель состояния аналитика между сессиями.
Это один markdown-файл, `<tasks.analysis_dir>/<EPIC>.md`, и он
отвечает на три вопроса при любом возобновлении работы: **на каком шаге остановились**,
**какие задачи ещё не доделаны** и **какие открытые вопросы остались**. Без состояния
каждая новая сессия начинает анализ заново и теряет согласованные предположения и решения.

Состояние хранит одну вещь, которая вообще не является состоянием работы аналитика, — **трассировку
`R<n>` → задача**. Эту таблицу читает *разработчик*, на шаге 1 своего пайплайна, возможно через
месяцы. Эта таблица отвечает на собственный вопрос аналитика — привязано ли каждое требование ровно
к одной задаче, — и на неё опирается шаг 4. Номера заканчиваются на границе эпика: тела задач несут
**текст** требований, а идентификаторы, попадающие в код, присваивает разработчик. Что состояние
всё-таки даёт разработчику, когда до него можно дотянуться, — картину, которой нет ни в одном тексте
задачи: какие требования ушли в **другие** задачи эпика. Сводный отчёт показывает ту же таблицу в
ответе и умирает вместе с сессией, поэтому состояние — передаваемый артефакт, а не черновик.

Состояние также хранит **реестр материалов** (схема БД, прежний код, цель, спеки и пр.)
со стабильными ID и **обоснования оценок** — чтобы ссылки не терялись, а оценки можно было
объяснить и пересмотреть между сессиями.

Состояние — **служебный файл, а не задача**: у него нет front-matter задачи
(`project/summary/ready/type`), он не должен попасть в JIRA.

## When to Use

- **В начале каждой сессии** — загрузить состояние и продолжить с зафиксированного шага;
  при первом заполнении «Контекста» и «Материалов» — сперва проверить `.pipeline/knowledge/`
  (скил `core/skills/project-knowledge/SKILL.md`).
- **В конце каждого шага `[STOP]`** и перед завершением сессии — обновить состояние.
- Когда пользователь спрашивает «на чём остановились / что осталось / какие вопросы открыты» —
  ответ берётся из состояния.
- При переключении между сценариями A/B/C — состояние сквозное, переносит контекст.

**When NOT to use:** одноразовый вопрос по коду без декомпозиции; состояние не нужно, если
артефактов-задач не будет.

## Process

### Шаг 1: Загрузить или создать состояние

1. **Вывести путь, а не спрашивать его.** Это `<tasks.analysis_dir>/<EPIC>.md`: каталог берётся
   из манифеста профиля, ключ эпика — из аргумента команды, и оба обязательны. Согласовывать
   нечего, значит и спрашивать нечего; назвать разрешённый путь.
2. Прочитать этот файл.
   - **Есть** → прочитать целиком. Восстановить: сценарий, текущий шаг, контекст,
     таблицу задач, реестр открытых вопросов, ASSUMPTIONS, «Следующее действие».
     Показать пользователю краткую сводку и предложить продолжить с этого места.
   - **Нет** → это новый эпик. Создать файл по тому же пути при первом сохранении.

### Шаг 2: Поддерживать состояние актуальным

После каждого шага обновлять соответствующие секции. Состояние — источник правды; блок
`STATE` в выводе каждого шага должен быть его краткой проекцией.

### Шаг 3: Сохранять безопасно (не как задачу)

Сканер издателя считает файл без валидного front-matter невалидной задачей, поэтому состояние
должно лежать там, куда сканер вообще не заглядывает. `<tasks.analysis_dir>/<EPIC>.md` — ровно такое
место: скан идёт по **одной папке эпика за раз** и читает только `.md`-файлы непосредственно в ней,
пропуская любые подкаталоги, а каталог анализа — сосед папок эпиков, а не файл внутри одной из них.
Он недосягаем по построению, а не из-за исключения, которое надо поддерживать.

**Этот путь единственный — и на запись, и на чтение.** Ни меню, ни вопроса: каталог — слот профиля,
ключ эпика — обязательный аргумент, а состояние, которое может лежать в любом из нескольких мест, —
это состояние, которое шаг 1 разработчика не найдёт. Носитель, который невозможно локализовать,
равен отсутствию носителя, а несёт он трассировку `R<n>` → задача.

Если профиль не объявляет `tasks.analysis_dir` — это дефект профиля: сказать об этом, положить
состояние рядом с папкой задач эпика, а не внутрь неё, и назвать путь в финальном ответе.

## Структура файла состояния

Полный шаблон — все секции, с примерами строк, показывающими ожидаемую форму, — в
[assets/state-template.md](./assets/state-template.md). Читать его целиком при создании нового
файла состояния или при сверке существующего с форматом; здесь он не воспроизводится — сводка
это ровно то место, где строка «Материалов» или колонка «Оценок» первой перестаёт совпадать
с тем, чего ждёт «Задачи».

Секции, которые он держит: **Мета** (эпик, сценарий, текущий шаг, статус сессии) · **Контекст**
(AS-IS / TO-BE, кратко) · **Материалы** (реестр ссылок, стабильные ID `M<n>` — сначала проверить
`.pipeline/knowledge/` через `core/skills/project-knowledge/SKILL.md`, прежде чем собирать вручную) ·
**Требования (EARS) и покрытие** (трассировка `R<n>` → задача, которую пайплайн разработчика читает
на своём шаге 1 — копируется дословно из реестра шага 2, никогда не переформулируется) · **Задачи** ·
**Оценки** (основание по ID материала) · **Открытые вопросы** · **Предположения** · **Журнал
решений** · **Следующее действие**.

## Common Rationalizations

| Рационализация | Реальность |
|---|---|
| «Я всё помню, состояние не нужно» | Контекст сессии конечен и сбрасывается. Состояние переживает компакт и новую сессию. |
| «Обновлю состояние в конце» | К концу часть решений забыта. Обновлять на каждом `[STOP]`. |
| «Положу состояние рядом с задачами как есть» | Без front-matter сканер издателя сочтёт его невалидной задачей. `<tasks.analysis_dir>/` вне его досягаемости по устройству — писать туда, а не рядом с задачами. |
| «Открытые вопросы и так в отчёте» | Отчёт показывается и теряется. Реестр вопросов в состоянии переживает сессию и ведёт сценарий C. |

## Red Flags

- Старт анализа без проверки, есть ли уже состояние в папке.
- AS-IS собран по коду с нуля, хотя в проекте есть `.pipeline/knowledge/<project>/modules/` с готовым описанием.
- Аналитик правит файлы в `.pipeline/knowledge/` — писать туда может только шаг 20 разработчика.
- Состояние не обновлялось несколько шагов и разошлось с реальностью.
- Ссылка на материал (схема БД, прежний код, спека) вписана прямо в задачу/оценку
  вместо реестра «Материалы» — дублируется и теряется при обновлениях.
- Оценка в таблице «Задачи» не совпадает со значением в секции «Оценки», или у оценки
  нет основания (ID материала) — непонятно, на чём она построена.
- В состоянии нет секции «Следующее действие» — при возобновлении непонятно, что делать.
- Таблицы требований и покрытия нет, или в ней привязки без формулировок: читатель получает
  «R7 → C2» и никакой возможности узнать, что в R7 написано. Номер без формулировки за пределами
  эпика не стоит ничего — а в разработку уезжает именно формулировка.
- Формулировка требования в таблице пересказана, а не скопирована — вторая, расходящаяся версия
  того же требования.
- Состояние сохранено как обычная задача (с front-matter задачи) — попадёт в JIRA.
- Блок `STATE` в выводе расходится с файлом состояния.

## Verification

- [ ] При старте состояние найдено и прочитано (или осознанно создано новое).
- [ ] Путь выведен из `tasks.analysis_dir` + ключа эпика, назван в ответе и не подхватывается
      сканером как задача.
- [ ] Заполнены: Мета, Контекст, реестр Материалов, таблица требований и покрытия, таблица Задач,
      Оценки, реестр Открытых вопросов, Следующее действие.
- [ ] Каждое `R<n>` из шага 2 есть в таблице требований и покрытия, с дословно скопированной
      формулировкой и привязкой одного из трёх видов; «существующая задача» и «отброшено» обоснованы.
- [ ] У каждой оценки есть основание (ID материала); значение совпадает с колонкой «Оценка».
- [ ] Ссылки на артефакты ведутся в реестре «Материалы» через ID, а не дублируются по тексту.
- [ ] Состояние обновлено в конце шага; блок `STATE` в выводе совпадает с файлом.
