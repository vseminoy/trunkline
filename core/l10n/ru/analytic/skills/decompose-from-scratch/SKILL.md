# Сценарий A: декомпозиция с нуля

## Overview

Взять эпик, разобраться в нём, разбить на задачи (Проблема → Решение → Как тестировать),
оценить каждую для разработчика уровня middle и упорядочить по зависимостям. Применяется, когда
**ничего ещё не декомпозировано**.

Режим — только чтение по коду (см. `rules/analytic-rules.md`). Единственные артефакты —
файлы задач по спеке формата, состояние анализа и сводный отчёт.

## When to Use

- Папка задач эпика пуста или задач по этому эпику ещё нет.
- На руках — описание фичи/бага/идеи, которое надо превратить в набор задач.

**When NOT to use:** задачи уже есть и их надо ревьюить/дооценить → `review-and-complete-tasks`;
надо закрыть открытые вопросы по готовым задачам → `resolve-open-questions`.

## Process

**У сценария A нет собственного процесса: его тело — это пайплайн.** Шаги лежат по одному
файлу в `core/analytic/steps/`: Прояснитель (0) → Диагност (1) → Аналитик (2) → Импакт-Аналитик (3)
→ Декомпозер (4) → Оценщик (5); таблица «шаг → файл» — в `core/analytic/PIPELINE.md`, раздел «Шаги».
Читать шаг там, прямо перед его выполнением, и следовать ему буквально.

Здесь они намеренно **не** пересказаны. Работоспособность этих шагов почти целиком держится на их
жёстких критериях остановки — пять проверяемых условий, заменивших «~95% уверенности» на шаге 0,
реестр требований в EARS как главный выход шага 2, признак дробления «больше 3 слоёв или 2 таблиц»
на шаге 4, контракт цикла сомнения, — а конспект это ровно то место, где такая детализация теряется.
Копия — это второе, что надо держать в согласии, и та, что лежала здесь раньше, уже разошлась
по четырём из этих пунктов.

Что относится к сценарию, а не к шагам:

- **Вход.** Сначала загрузить или создать состояние (`analysis-state`, сценарий = A). После каждого
  шага — `[STOP]` и обновление состояния.
- **Всё строится, а не сверяется.** В отличие от B и C здесь нет ни существующих задач, с
  которыми надо согласовываться, ни реестра, который надо восстанавливать: шаг 2 строит реестр
  `R<n>` с нуля, и он же — источник для всех последующих шагов.
- **Выход.** Трассировка `R<n>` → задача уходит в таблицу «Требования (EARS) и покрытие»
  состояния — именно её читает пайплайн разработчика на своём шаге 1. Сводный отчёт показывается
  в ответе как вид на ту же таблицу. Оба описаны на шаге 5.

Оценка — таблица размеров, коэффициенты затухания по слоям, множитель для тонкого прокси, плоская
ставка на миграции — лежит у Оценщика (шаг 5) и тоже здесь не конспектируется: копия этой таблицы
без правил затухания даёт оценки примерно вдвое завышенные.

## Одна задача вместо эпика

На входе — описание **одной** задачи и ключ эпика, к которому она относится, а просят описать
именно её, а не сделать декомпозицию. Это тот же сценарий с областью в одну задачу, а не отдельный
сценарий: задачу пригодной для разработчика делают реестр требований шага 2 и правила оформления
шага 5, и ровно их потерял бы отдельный пересказанный маршрут.

**Маршрут — `1 → 2 → 3 → 4 → 5`.** Шаг 0 выполняется, если описание расплывчато, как и везде.

**Шаг 4 не дробит — он проверяет.** Делить нечего, поэтому от него остаётся то, что не про деление:
потолок 24 ч и доверительный цикл. Если требования шага 2 набирают больше 24 часов — это **и есть**
ответ на запрос: пришедшее как одна задача есть несколько, и результатом становится разбиение, а не
единственный файл, который просили. Сказать это прямо и оставить решение пользователю. Из критериев
остановки без изменений работают 1, 2, 4 и 5 (ничего не потеряно, ничто не привязано дважды, ни одно
требование не разрезано, `IF … THEN` не оторван от своего `WHEN`); 3 при одной задаче истинен
тривиально; 7 сводится к тому, за чем эта задача должна следовать.

**Номера продолжают нумерацию эпика, а не начинаются заново.** Состояние — тот же файл
`<tasks.analysis_dir>/<EPIC>.md`. Если он есть, прочитать таблицу «Требования (EARS) и покрытие» и
нумеровать после наибольшего `R<n>`: номера сквозные по **эпику** и не переиспользуются, а вторая
задача, пронумерованная с `R1`, столкнётся с первой в тот момент, когда обе прочитают вместе. Если
файла нет — создать: требования этой задачи и есть первые требования эпика, а следующий прогон
продолжит после них. В обоих случаях таблица покрытия получает строки с якорем на эту задачу, а
требования других задач эпика — там, где файл их уже знает, — говорят, чего этой задаче делать
**не** нужно.

**Оценка считается как обычно** — шаг 5 целиком, с затуханием по слоям, множителем характера и
плоской ставкой на миграции. Сводный отчёт вырождается в одну строку, и это нормально; не
вырождается блок «Риски и открытые вопросы» и правило про расхождение больше чем в 1.5 раза между
двумя способами оценки — на одной задаче это единственный сигнал, что её границы выбраны неверно.

**Публикация.** Один файл — значит операция издателя на одну задачу
(`tasks.publisher.operations.publish_one`), а не на весь эпик. Создание и обновление она различает по
правилу из спеки формата: файл, во front-matter которого уже стоит ключ задачи в трекере,
**обновляет** её, файл без ключа создаёт новую. Так задача, которая в трекере уже есть, сохраняет
свой ключ и историю — проверить наличие ключа в файле до того, как предлагать операцию: публикация
без него и создаёт дубль. Как и везде на этой ветке, запускает её пользователь.

## Common Rationalizations

| Рационализация | Реальность |
|---|---|
| «Задача понятная, пропущу Прояснителя» | Если нет acceptance criteria — она не понятная. Прояснить дёшево сейчас. |
| «Разобью горизонтально: вся БД, потом хендлеры» | Горизонтальные слайсы не дают рабочих инкрементов. Резать вертикально. |
| «Эта задача ~30 ч, оставлю как есть» | Потолок 24 ч жёсткий. Вернуть Декомпозеру и раздробить. |
| «Сохраню файлы, папку и так понятно» | Она и правда понятна — это `<tasks.dir>/<ЭПИК>/` из манифеста. Объявить разрешённый путь, согласовать front-matter, сохранить. Спросить «в какую папку» — это как раз способ получить ответ, расходящийся со слотом. |
| «Задача одна, обойдусь без реестра — просто напишу файл» | Блок «Как проверить» и **есть** реестр, один пункт на требование. Пропустить шаг 2 — значит оставить шаг 7a разработчика без того, что он считает: единственной механической проверки, натянутой между двумя ветками. |
| «Задача одна, значит нумерация с R1» | Номера сквозные по эпику. Прочитать состояние и продолжить с наибольшего. |
| «Шаги я знаю, буду работать по этому файлу» | Этот файл — роутер. Шаги и их критерии остановки — в `core/analytic/steps/`; работа по конспекту это и есть тот путь, на котором теряются реестр и цикл сомнения. |

## Red Flags

- Начало декомпозиции без собранного контекста и без ASSUMPTIONS.
- Задача без чётких Проблема/Решение/Как тестировать.
- Задачи не упорядочены по зависимостям; фундаменты не первыми.
- Файлы сохранены без чтения спеки формата и без согласования с пользователем.
- Состояние не создано — следующая сессия начнёт заново.
- Шаг пройден без проверки его критерия остановки, потому что критерий не читали.

- [ ] Сводный отчёт с оценками показан пользователю.
