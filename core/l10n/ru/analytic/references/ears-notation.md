# Нотация требований — EARS

Функциональные требования и критерии приёмки формулируются в нотации **EARS** (Easy Approach to Requirements Syntax). Это единый источник правды по форме требований для Прояснителя (шаг 0) и Аналитика (шаг 2).

Ключевые слова пишутся **ЗАГЛАВНЫМИ** и используются только в своём значении: `КОГДА`, `ПОКА`, `ЕСЛИ … ТО`, `ГДЕ`, `ДОЛЖЕН/ДОЛЖНА/ДОЛЖНО`.

**Пять шаблонов:**

| Тип | Шаблон | Когда применять |
|---|---|---|
| Вездесущее | `<Система> ДОЛЖНА <реакция>.` | действует всегда, без условий (инварианты) |
| Событийное | `КОГДА <триггер>, <система> ДОЛЖНА <реакция>.` | реакция на событие/запрос — основной тип для эндпоинтов |
| Состояние | `ПОКА <состояние>, <система> ДОЛЖНА <реакция>.` | действует на интервале, пока держится режим |
| Нежелательное | `ЕСЛИ <нежелательный триггер>, ТО <система> ДОЛЖНА <реакция>.` | ошибки, таймауты, отказы, невалидный вход |
| Опциональность | `ГДЕ <функция включена>, <система> ДОЛЖНА <реакция>.` | feature flag, опция конфигурации, тарифная опция |

**Составные требования** — комбинация в строгом порядке `ГДЕ → ПОКА → КОГДА/ЕСЛИ → ДОЛЖНА`, **не более двух условий**. Три и больше условий = это не требование, а алгоритм; разбить на несколько.

Пример:
```
ПОКА абонент находится в статусе «заблокирован», КОГДА поступает запрос на активацию услуги,
сервис ДОЛЖЕН вернуть 409 и код ошибки SUBSCRIBER_BLOCKED.
```

**Правила формулирования:**
- **Субъект обязателен.** «Должна быть реализована валидация» — запрещено: непонятно, чья это ответственность. Всегда указывать систему/сервис/слой.
- **Реакция проверяема.** Не «учитывает статус», а «возвращает 409 и код `SUBSCRIBER_BLOCKED`». Формулировки «корректно обработать», «правильно отработать», «адекватно среагировать» — запрещены: формально это EARS, содержательно это пустое требование.
- **Одно требование = один тест.** Если из требования нельзя написать один конкретный тест — оно сформулировано неверно.
- **Привязка к контракту.** Где требование относится к эндпоинту — ссылаться на идентификатор операции из контракта. Структуру запроса/ответа (поля, типы) в EARS **не дублировать** — она живёт в спеке. EARS описывает **поведение**: при каких условиях возвращается именно этот код, а не структуру данных.
- **Идентификаторы.** Каждое требование получает сквозной идентификатор `R1`, `R2`, … — по ним идёт трассировка в Импакт-Анализе, Декомпозиции и в блоке «Как тестировать» задач.
- **Идентификатор — рабочая пометка этого эпика, а не контракт вниз по потоку.** Разработчик (`core/developer`) переиспользует `R<n>` как есть: тот же номер уходит в контракт, комментарий к констрейнту и таблицу тестов. Отсюда два следствия:
  - **Номер не переприсваивается никогда** — ни при пересмотре формулировки, ни между сессиями, ни при переносе требования в другую задачу. Требование отменено — `R<n>: [ОТМЕНЕНО]`, номер не отдаётся другому.
  - **Трассировка `R<n>` → задача служит этому эпику и заканчивается на его границе.** Она отвечает на вопрос самого аналитика — привязано ли каждое требование ровно к одной задаче — и живёт в **состоянии анализа** (`<tasks.analysis_dir>/<EPIC>.md`, таблица «Требования (EARS) и покрытие»), которое по построению сохраняется на каждом шаге. К разработке переезжает **текст** требования, в блоке «Как тестировать»; идентификаторы, попадающие в код, присваивает разработчик на своём шаге 2 и записывает, из какого пункта они выведены, — так что потеря на передаче видна по счёту. Не писать `R<n>` в тело задачи: номер, который что-то значит внутри эпика и ничего снаружи, хуже отсутствия номера, потому что выглядит контрактом.

**Параметризованные требования.** Если поведение одинаково по форме, но отличается набором значений (по `purpose`, по каналу, по типу документа) — это **одно требование плюс таблица параметров**, а не по требованию на значение. Таблица значений идёт в раздел «Вне EARS» как данные.

Правильно:
```
R9. КОГДА получен запрос с purpose=<P>, сервис ДОЛЖЕН применить шаблон текста, длину кода,
    TTL, интервал повтора и max attempts из конфигурации purpose <P>.
    (значения — таблица «Параметры purpose» в разделе «Вне EARS»)
```
Неправильно: семь отдельных требований `R9…R15`, по одному на каждый `purpose`. Это раздувает реестр, ломает оценку и провоцирует ненужное дробление задач.

Критерий: если требования отличаются **только значениями в одних и тех же местах** — сворачивать в одно. Если у какого-то значения появляется **своя ветка поведения** (иной набор шагов, иной код ответа) — это отдельное требование.

**Что в EARS НЕ формулируется** (пишется отдельно, прозой/таблицами — попытка натянуть EARS на это является ошибкой):
- нефункциональные требования (RPS, латентность, лимиты);
- структура данных и форматы полей — это контракт и SQL-схема;
- бизнес-цель и мотивация («зачем») — это блок «Проблема» в задаче;
- сложные расчётные алгоритмы — таблицы решений или псевдокод.

Реалистичное покрытие — 60–70% функциональной части постановки. Остаток прозой; не подгонять.

**Вездесущие требования из guidelines.** Правила из гайдлайнов профиля (авторизация, миграции, типы данных) действуют для всех задач по умолчанию. В требования конкретной задачи их **не переписывать** — только ссылаться, если задача явно их нарушает или требует исключения.
