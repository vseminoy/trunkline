# Шаг 4. Агент-Декомпозер `[STOP]`

**Скилы:** `agent-skills/skills/planning-and-task-breakdown/SKILL.md`, `agent-skills/skills/doubt-driven-development/SKILL.md`

Разбивает эпик на задачи. Применять полный процесс из скила.

**Единица разбивки — требование.** Декомпозиция идёт по реестру `R<n>` из шага 2: задача — это связная группа требований, а не «кусок работы на глаз». Это делает дробление проверяемым, а не интуитивным.

**Принципы разбивки:**
- **Вертикальные слайсы**, не горизонтальные: каждая задача — законченный кусок функциональности (по возможности от контракта/БД до хендлера и тестов), а не «вся БД отдельно, все хендлеры отдельно». Исключение — фундаментные задачи, от которых зависят остальные (контракт, схема, миграция): они выделяются отдельно и идут первыми.
- **Каждая задача ≤ 24 рабочих часа** для middle-разработчика (см. таблицу оценок в `core/analytic/steps/a05-estimator.md`). Если больше — дробить дальше.
- **Требование не дробится между задачами.** Одно `R<n>` реализуется целиком в одной задаче. Если требование не влезает в 24 часа — это не проблема декомпозиции, а признак того, что требование слишком крупное: вернуть Аналитику (шаг 2) на разбиение, а не разрезать его по задачам. Разрезанное требование невозможно проверить одним тестом, и это ломает всю трассировку.
- **`ЕСЛИ … ТО` идёт вместе со своим `КОГДА`.** Требование на ошибочный сценарий попадает в ту же задачу, что и основной сценарий, к которому оно относится. Выносить обработку ошибок в отдельную задачу «на потом» запрещено — именно так ошибочные ветки и не доезжают до прода.
- Признаки, что задачу нужно дробить ещё: в названии есть «и»; затрагивает две независимые подсистемы; не описывается одним абзацем.
- Задача должна оставлять систему в рабочем состоянии (где это применимо).

**Чем мерить размер: точки изменения, а не количество требований.** Считается число затронутых **слоёв и таблиц**, а не число `R<n>`. Двенадцать требований к одному сервису с одной таблицей и двумя эндпоинтами — это **одна** здоровая задача (общий каркас, общие тесты); два требования к двум разным подсистемам — это **две** задачи.

Сигнал к дроблению: больше **3 слоёв** или больше **2 таблиц** в одной задаче. Количество требований само по себе сигналом не является — восемь ошибочных веток одного хендлера дробить незачем.

**Матрица покрытия (обязательный артефакт).** Каждое требование получает привязку одного из **трёх** видов:

| Вид привязки | Значение | Когда |
|---|---|---|
| Новая задача | префикс (`C2`) | требование реализуется в этом прогоне |
| Существующая задача | JIRA-ключ (`DEMO-793`) | требование уже покрыто заведённой задачей — новую не плодим |
| Отброшено | `— <причина>` | требование уже реализовано в коде, либо выведено из скоупа решением пользователя |

```
| ID | Требование (кратко)            | Привязка                        |
|----|--------------------------------|---------------------------------|
| R1 | создание абонента → 201        | C2                              |
| R2 | дубль номера → 409             | C2                              |
| R3 | 503 на время миграции          | C1                              |
| R4 | отправка SMS через шлюз        | DEMO-546 (Closed, реализовано)   |
| R5 | Telegram-канал                 | — вне скоупа, решение пользователя |
```

Привязки видов «существующая задача» и «отброшено» **обязательно обосновываются одной строкой** — со ссылкой на код (что именно уже реализовано) или на директиву пользователя. Отбрасывание требования без обоснования запрещено: это тихая потеря скоупа.

### Проверка декомпозиции свежим контекстом (ОБЯЗАТЕЛЬНО)

Ошибка в декомпозиции дороже ошибки в коде: она размножается на все задачи и всплывает
уже у разработчика. Поэтому раскрой эпика **не принимается на веру собственным контекстом** —
он проходит цикл `CLAIM → EXTRACT → DOUBT → RECONCILE → STOP` из `doubt-driven-development`.

Применение цикла к декомпозиции:

1. **CLAIM.** Сформулировать утверждение, которое проверяем, напр.: «матрица покрытия полна
   и непротиворечива: каждое `R<n>` привязано ровно один раз, лишних задач нет».
2. **EXTRACT.** Собрать минимальный проверяемый артефакт: **реестр требований (шаг 2) + матрица
   покрытия + список задач с границами**. Свои рассуждения о том, почему раскрой именно такой,
   в артефакт **не включать**.
3. **DOUBT.** Запустить ревьюера **свежим контекстом** (субагент) с состязательным промптом.
   Передавать **только ARTEFACT + CONTRACT, без CLAIM** — иначе ревьюер подстраивается под вывод.
   CONTRACT для этого шага — пункты 1–7 критерия остановки ниже.
   Спрашивать: какое требование потеряно, какое разрезано между задачами, какая задача
   не покрывает ни одного `R<n>`, где `ЕСЛИ … ТО` оторвано от своего `КОГДА`, какое обоснование
   отбрасывания не выдерживает проверки.
4. **RECONCILE.** Каждую находку классифицировать по тексту артефакта: подтверждена (правим
   декомпозицию) / отклонена (с обоснованием) / вне скоупа. Молча игнорировать находки запрещено.
5. **STOP.** Не более **3 циклов**; выход раньше — когда остаются только тривиальные находки.

Если цикл вскрыл потерянное или разрезанное требование — это дефект **шага 2**, а не шага 4:
вернуться к Аналитику, а не «дособирать» реестр в декомпозере (см. правило после критерия остановки).

Результат цикла (что проверяли, что нашли, что исправили) фиксируется в сводном отчёте одним абзацем.

### Критерий остановки (ЖЁСТКИЙ)

**Применимость.** Пункты 1–5 действуют, **только если реестр требований существует** — то есть в сценарии A, где отработал Аналитик (шаг 2). В сценариях B и C реестра нет (см. «Трассировка в сценариях B и C» ниже) — там проверяются только пункты 6–7.

Декомпозер выходит на `[STOP]` **только когда выполнены ВСЕ применимые пункты**:

1. **Полнота.** Каждое `R<n>` из реестра шага 2 присутствует в матрице покрытия — с привязкой любого из трёх видов. Требований без привязки нет.
2. **Отсутствие дублей.** Каждое `R<n>` привязано ровно к **одной** задаче (для привязки вида «новая задача»).
3. **Отсутствие лишнего.** Каждая задача покрывает хотя бы одно `R<n>`. Задача, не привязанная ни к одному требованию, — это либо расширение скоупа (убрать), либо пропущенное требование (вернуть Аналитику на шаг 2). Исключение — чисто инфраструктурные фундаменты (заведение миграции, генерация из спеки): помечаются явно как `инфра` и обосновываются одной строкой.
4. **Целостность требований.** Ни одно `R<n>` не разрезано между задачами.
5. **Ошибочные сценарии на месте.** Каждое `ЕСЛИ … ТО` лежит в той же задаче, что и связанное с ним `КОГДА`.
6. **Обоснования проставлены.** Каждая привязка вида «существующая задача» и «отброшено» сопровождается строкой обоснования.
7. **Порядок согласован с импакт-анализом.** Ограничения порядка из шага 3 отражены в графе зависимостей.
8. **Цикл сомнения пройден** (действует во всех сценариях, включая B и C). Ревью свежим контекстом
   выполнено, все находки классифицированы, стоп-условие достигнуто. Пропуск цикла допустим только
   по явному указанию пользователя и **фиксируется в отчёте** — молчаливый пропуск запрещён.

При нарушении пунктов 1, 3 или 4 — **не «дособрать самому», а вернуться к соответствующему шагу** (2 или 3) и сообщить пользователю, что именно разошлось.

### Трассировка в сценариях B и C

Сценарии B (ревью + дооценка) и C (закрытие вопросов) входят в пайплайн **без шага 2**, поэтому реестра `R<n>` у них нет. Работа в них идёт так:

- **По умолчанию трассировка не применяется.** Декомпозер работает по существующим задачам; критерии 1–5 пропускаются с явной пометкой «реестр требований отсутствует (сценарий B/C)».
- **Реестр можно восстановить** — если пользователь просит проверить полноту покрытия. Источник: блоки «Как тестировать» уже оформленных задач + требования из связанных задач JIRA. Восстановленный реестр помечается как таковой, и по нему проверяются пункты 1–5 в обычном режиме.
- **Цикл сомнения применяется и здесь**, но артефактом для EXTRACT становится не матрица покрытия,
  а **набор существующих задач**, а CONTRACT — спека формата плюс полнота покрытия
  относительно описания задачи. Вопрос ревьюеру меняется с «что потеряно из реестра» на
  «какой сценарий из описания задачи не покрыт ни одной задачей».
- **Gap-анализ.** Когда часть требований покрыта задачами, уже заведёнными в JIRA, — это штатная ситуация, а не пробел: такие требования получают привязку вида «существующая задача». Не заводить на них новые задачи.

**Построить граф зависимостей** (что от чего зависит) и упорядочить снизу вверх — фундамент первым:
```
схема БД / миграция → запросы к БД → сервис → хендлер → потребители контракта
контракт            → кодогенерация → хендлер
```
(конкретные слои и инструменты — из `layers` и `stack` профиля)

**ВАЖНО: режим только чтения.** Запрещено менять код, создавать файлы проекта, запускать изменяющие команды.

**Выход:** список задач с черновыми границами, матрица покрытия `R<n>` → задача и предварительный граф зависимостей.
