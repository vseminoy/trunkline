# Шаг 3. Агент-Импакт-Аналитик `[STOP]`

**Скилы:** `agent-skills/skills/deprecation-and-migration/SKILL.md`

Оценивает влияние изменений на слои из `layers` профиля, а также на миграции и авторизацию.

- Определить, что меняется: контракт (спека) / схема БД / сервисный слой / хендлеры.
- Backward compatibility: ломаются ли существующие контракты/потребители.
- Если запрос включает удаление/замену кода — Zombie Code проверка (`grep -r "ИмяФункции" .`) и выбор стратегии (Parallel-run / Strangler Fig / Adapter / Feature Flag / Big Bang).

Это нужно, чтобы декомпозиция учитывала **порядок**: контракт и миграции обычно идут раньше зависящего от них кода.

**Работа по реестру требований.** Импакт-анализ идёт **по требованиям `R<n>` из шага 2**, а не по эпику в целом: для каждого требования определяется, какие слои оно затрагивает и что в них меняется. Требования служат точками привязки — `КОГДА получен запрос …` указывает на handler и контракт, `ПОКА идёт миграция …` — на слой миграций.

Результат сводится в таблицу:

| ID | Затрагиваемые слои | Что меняется | Ломает совместимость |
|----|--------------------|--------------|----------------------|
| R1 | контракт, handler, service | новая операция в спеке | нет |
| R2, R4–R7 | service | только логика (ветки валидации) | нет |
| R3 | migration, шлюз | новая миграция | да — 503 на запись |

**Группировать одинаковое.** Требования с идентичным импактом сводятся в одну строку через перечисление ID (`R2, R4–R7`). Развёрнутая таблица на 13 строк, из которых 11 совпадают, — это шум: она не даёт Декомпозеру никакой дополнительной информации. Разворачивать построчно только там, где импакт **различается**.

Требование, для которого не удаётся назвать ни одного слоя, — признак того, что оно сформулировано слишком абстрактно либо не относится к этой системе: вернуть Аналитику (шаг 2), а не проносить дальше.

**Выход:** затронутые слои и риски **в разрезе `R<n>`**, ограничения порядка (что должно идти раньше чего).
