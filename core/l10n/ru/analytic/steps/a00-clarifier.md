# Шаг 0. Агент-Прояснитель `[CONDITIONAL]`

**Скилы:** `agent-skills/skills/interview-me/SKILL.md`, `agent-skills/skills/idea-refine/SKILL.md`
**Справка:** `core/analytic/references/ears-notation.md`

Запускается, если запрос размыт: нет конкретного поведения, нет acceptance criteria, неясны границы, нет указания на эндпоинты/слои.

Применять процесс из скилов: один вопрос за раз, пока не будет достигнут критерий остановки (см. ниже). Дополнительно уточнять:
- какие слои затронуты — по списку `layers` профиля;
- ограничения стека — по `stack` профиля;
- что считается «готово» (acceptance criteria) для запроса в целом.

### Критерии приёмки — в EARS

Критерии приёмки на выходе Прояснителя оформляются **в нотации EARS** (см. «Нотация требований — EARS», `core/analytic/references/ears-notation.md`). Это верхнеуровневые критерии для запроса целиком — 3–7 требований; детальную проработку делает Аналитик на шаге 2.

**EARS здесь — это инструмент опроса, а не оформления.** Механика такая: агент пытается записать понимание запроса шаблоном. Место, где шаблон не заполняется, и есть следующий вопрос пользователю:

| Что не заполняется | Какой вопрос задать |
|---|---|
| нет субъекта в `<система> ДОЛЖНА` | какой сервис/слой отвечает за это поведение? |
| нет реакции или она непроверяема | что конкретно система возвращает/делает? какой код ответа? |
| не выбирается между `КОГДА` и `ПОКА` | это разовое событие или состояние, которое держится во времени? |
| нет ни одного `ЕСЛИ … ТО` | что должно произойти, если <внешняя система/валидация/таймаут> откажет? |
| условий больше двух | это точно одно требование? какие из условий можно вынести отдельно? |

### Критерий остановки (ЖЁСТКИЙ)

Прояснитель завершает работу и выходит на `[STOP]` **только когда выполнены ВСЕ пункты**:

1. Каждый критерий приёмки записан одним из пяти шаблонов EARS — без «примерно», «в целом», «и т.п.».
2. У каждого критерия есть **субъект** (конкретная система/сервис/слой) и **проверяемая реакция**.
3. Есть **хотя бы одно** требование типа `ЕСЛИ … ТО` (нежелательное поведение). Если ошибочных сценариев действительно нет — это пишется явной строкой с обоснованием, а не пропускается молча.
4. Границы запроса зафиксированы: сказано не только что входит, но и **что НЕ входит** в запрос.
5. Ни один критерий не содержит запрещённых формулировок («корректно обработать», «правильно отработать», «работает как ожидается»).

**Пока хотя бы один пункт не выполнен — задавать следующий вопрос, а не переходить к шагу 1.** Формулировка «~95% уверенности» заменена этим списком: он проверяем, а ощущение уверенности — нет.

Если пользователь отказывается отвечать или ответа нет — **не угадывать**: вынести незакрытое в `ASSUMPTIONS` с явной пометкой «не подтверждено» и передать в Open Questions Аналитика.

**Выход:** запрос переформулирован с явными границами (включая «что НЕ входит») и критериями приёмки в EARS, прошедшими критерий остановки.
