# AGENTS.md — entry point for coding agents

This repository is **trunkline**: a vertical, brownfield spec-driven development pipeline plus the
CLI that installs it into a project.

You are most likely here for one of two reasons. Pick the right one before doing anything else.

## A. You are running the pipeline on some other project

You are in the wrong repository. trunkline vendors itself into the target project; the entry point
there is `.trunkline/AGENTS.md`, generated by `trunkline init`. Read that file, not this one.

```bash
trunkline init --profile <name>   # in the target project
```

## B. You are working on trunkline itself

Read in this order:

1. `README.md` — what the product is and how it is installed.
2. `core/README.md` — the boundary between the stack-agnostic core and the stack profiles. This is
   the rule most changes get wrong.
3. `core/developer/PIPELINE.md` — the developer pipeline core (the largest single artefact).
4. `core/ORCHESTRATION.md` — what a host agent must be able to do, and what merely degrades.
   `docs/DESIGN-NOTES.md` — why the core's rules are what they are; read it before arguing with one,
   and put new justifications there rather than in the core.
5. `profiles/README.md` — how a stack profile is built.

### The gates that must pass before a commit

```bash
python3 scripts/lint-core-profile-boundary.py   # core ↔ profile boundary
python3 scripts/lint-pipeline-paths.py          # core paths resolve from the pipeline root
python3 scripts/lint-l10n.py                    # localizations vs their English sources
node scripts/lint-own-skills.js                 # structure of our own skills
node scripts/run-own-evals.js                   # skill routing by description
go build ./... && go vet ./...                  # the CLI
```

The first one is the important one: it fails if stack vocabulary (a language, a tool, a build
command) leaked into `core/`, if a step references a manifest slot that no profile declares, or if a
step overlay is orphaned. Discipline alone does not hold that boundary — the gate does.

### Rules specific to this repository

- **Nothing stack-specific in `core/`.** If a sentence starts with "in \<language\> we usually", it
  belongs in `profiles/<name>/`, either in the guidelines or in a step overlay declared under
  `step_overlays`.
- **`core/` is English.** Russian stays in `profiles/`, in the docs, and in `core/l10n/ru/`.
- **Editing an English core file obliges you to its translations.** `core/l10n/<lang>/` mirrors
  `core/`, and `scripts/lint-l10n.py` fails when a source changed and its translation did not.
  Redo the translation, then `--update <lang>`. Running `--update` to silence the gate encodes a
  lie in the lock file and makes the drift invisible.
- **`agent-skills/` is a read-only submodule** (upstream `addyosmani/agent-skills`). Never edit it;
  update it with `git submodule update --remote agent-skills`.
- **Do not duplicate content between prompts** — link to it. A second copy is a second thing to keep
  in sync, and it will not stay in sync.
- **Changing a skill's `description` means rerunning the evals.** Routing rests entirely on those
  descriptions.

### Layout

```
core/         the pipeline: stack-agnostic, English (incl. core/developer/scripts/, which ships
              into a project and runs there — not a repo gate)
profiles/     stack profiles: language, commands, guidelines, overlays
publishers/   task-publisher contracts (owned by the tool, shared by profiles)
internal/     the trunkline CLI (install, migrate, doctor, profile, state)
cmd/trunkline the CLI entry point
assets.go     the embedded payload (core + profiles + the agent-skills subset)
evals/        routing test cases, one file per skill
scripts/      the gates above
```
