# ТЗ: MCP-сервер для создания задач в JIRA из markdown-файлов

## 1. Цель

MCP-сервер на Go, который читает задачи, описанные в markdown-файлах из заданной
папки, и создаёт их в JIRA внутри определённого эпика. Сервер запускается
локально и подключается к Claude Code (или другому MCP-клиенту) по транспорту
**stdio**.

## 2. Окружение JIRA

| Параметр | Значение |
|---|---|
| Тип | JIRA **Server / Data Center** (свой домен компании) |
| Base URL | `https://jira.example.com` |
| Версия REST API | **v2** (`/rest/api/2/...`) |
| Формат описаний | wiki-markup / plain text (не ADF) |
| Авторизация | **Personal Access Token**, заголовок `Authorization: Bearer <token>` |

## 3. Конфигурация (env-переменные)

Конфиг читается из env. Локально — из файла окружения проекта.

> ⚠️ Текущий файл назван `.evn` (опечатка) — переименовать в `.env`.
> ⚠️ Файл с токеном обязательно добавить в `.gitignore` — секрет не должен попасть в репозиторий.

| Переменная | Назначение | Пример |
|---|---|---|
| `JIRA_URL` | base URL инстанса | `https://jira.example.com` |
| `JIRA_PERSONAL_ACCESS_TOKEN` | PAT для Bearer-авторизации | *(уже задан в `.evn`)* |
| `JIRA_EPIC_FIELD` | id кастомного поля «Epic Link» | `customfield_10008` |
| `TASKS_DIR` | корневая папка с эпик-папками задач | `./tasks` |

`JIRA_EPIC_FIELD` определяется один раз автоматически (см. §7) и фиксируется в конфиге.

**Эпик — из имени папки.** Внутри `TASKS_DIR` лежат подпапки, имя каждой = ключ
эпика (`PROJ-855`, `DEMO-100`), а в них — `.md`-файлы задач. Поэтому отдельной
переменной `JIRA_EPIC` нет: целевой эпик задачи определяется именем её папки
(см. [docs/task-format.md](./task-format.md) §2).

## 4. Формат markdown-файла

Формат документа задачи (обязательный YAML front-matter + тело) вынесен в
отдельную спецификацию — единый источник правды:

> **[docs/task-format.md](./task-format.md)**

Ключевое для остальной части ТЗ:

- **Один файл = одна задача**; front-matter **обязателен**.
- Обязательные поля: `project`, `summary`, `ready`, `type`.
- **`project`** — ключ JIRA-проекта задачи; задаётся в каждом файле (поэтому
  отдельной env-переменной `JIRA_PROJECT` нет).
- **`ready` — гейт**: `true` → задачу заводим и переносим файл в `done/`. Для
  `false` сервер **спрашивает**, публиковать ли «не готовые»: при «нет» —
  пропускаем; при «да» — задачу всё равно заводим, но файл **не переносим** и
  проставляем ему `jira_key`, чтобы следующий прогон её **обновлял**, а не
  дублировал (см. §5).
- **Эпик берётся из имени папки**, в которой лежит файл (см. §3, §5).
- **Приоритет** всегда `Medium` (отдельного поля нет).
- **`links`** — список **блокирующих** задач; на каждую создаётся связь
  `is blocked by`. Может быть пустым. Элемент — либо **JIRA-ключ** (`PROJ-900`),
  либо **локальная ссылка** на файл из этой же папки по префиксу (`C1`).
- **Порядок заведения — по буквенно-числовому префиксу имени файла** (`B1`, `C1`,
  `C2`…): по букве, затем по числу. Блокер имеет меньший префикс и заводится
  раньше; его новый ключ запоминается и подставляется в связь зависимой задачи
  (резолв локальных ссылок, см. §7, §10).
- **`attachments`** — файлы из «папки задачи» (подпапка рядом с `.md`, имя =
  имя файла без расширения); грузятся в JIRA после создания задачи. Строгая
  проверка: нет файла или превышен лимит размера → задача не создаётся (см. §7).
- **Картинки в описании** — markdown `![](pic.png)` в теле: файл из папки задачи
  загружается как вложение **автоматически**, а ссылка переписывается в JIRA-wiki
  `!pic.png!` для отрисовки в описании (см. §7 и task-format §4.1).
- После создания задачи MCP дописывает в файл `jira_key` / `jira_url` /
  `jira_created_at` (см. §5).

## 5. Защита от дублей и хранение связи «файл → задача»

**Гейт `ready` и вопрос о публикации «не готовых».** Перед запуском пачки сервер
**спрашивает пользователя**, публиковать ли задачи со статусом `ready: false`.
От ответа зависит, какие файлы уходят в JIRA:

- **Ответ «нет» (по умолчанию)** — публикуются **только** `ready: true`. Файлы
  `ready: false` **пропускаются**, задача не создаётся, файл **не перемещается** и
  ключ ему **не проставляется** (остаётся черновиком до следующего прогона).
- **Ответ «да»** — в JIRA отправляются **все** задачи (`ready: true` и
  `ready: false`). Разница только в том, что происходит с файлом после успешной
  отправки (см. ниже).

Технически ответ передаётся параметром инструмента (напр. `publish_unready: bool`,
см. §6); вопрос задаётся пользователю перед запуском пачки.

**Что происходит после успешной отправки задачи в JIRA.** В front-matter файла в
любом случае дописываются поля задачи:

- `jira_key: <KEY>` — ключ задачи (напр. `DEMO-123`);
- `jira_url: <BASE_URL>/browse/<KEY>` — прямая ссылка на задачу;
- `jira_created_at: <ISO-8601>` — когда создана.

Дальше судьба файла зависит от `ready`:

- **`ready: true`** — файл перемещается в подпапку `done/` **внутри своей
  эпик-папки** (`TASKS_DIR/<EPIC>/done/`). Если у задачи есть «папка задачи» с
  вложениями (см. §7), она перемещается **вместе** с `.md`. Задача считается
  завершённой, повторно не обрабатывается. Это правило действует **и при
  обновлении**: если файл с уже проставленным `jira_key` дозрел до `ready: true`,
  задача обновляется (`PUT`) и файл **переносится в `done/`** в том же прогоне.
- **`ready: false`** (отправлена при ответе «да») — файл **остаётся на месте**
  (не переезжает в `done/`), но уже **с проставленным `jira_key`**. Это значит,
  что при **следующем** прогоне он будет подхвачен сканером, но **не как новая
  задача**: наличие `jira_key` переключает обработку в режим **обновления по
  этому ключу** (`PUT /rest/api/2/issue/{key}`, см. §7), а не создания. Так
  черновик можно дорабатывать и многократно синхронизировать с уже заведённой
  задачей JIRA, пока он не станет `ready: true` и не уедет в `done/`.

**Префикс `WIP: ` в заголовке для черновиков.** Заголовок задачи в JIRA зависит
от `ready` на момент отправки:

- При создании задачи со статусом **`ready: false`** к `summary` спереди
  добавляется префикс **`WIP: `** (Work In Progress) — в JIRA уходит заголовок
  `WIP: <summary>`. Так в трекере сразу видно, что это ещё черновик.
- Когда такая задача **обновляется со статусом `ready: true`**, префикс `WIP: `
  из заголовка **убирается** — задача получает чистый `summary`. (Если на момент
  апдейта заголовок начинается с `WIP: `, этот префикс снимается; повторное
  добавление при `ready: true` не делается.)
- В самом markdown-файле поле `summary` всегда хранится **без** `WIP: ` —
  префикс это деталь представления в JIRA, он добавляется/снимается только в
  отправляемом заголовке, не в файле.

После любой успешной отправки запись добавляется/обновляется в **реестре**
`TASKS_DIR/index.json` — едином машиночитаемом списке соответствий по всем эпикам.

**Различение «создать» vs «обновить»** при обходе — по наличию `jira_key` во
front-matter файла, который сканер встретил вне `done/`:

- **нет `jira_key`** → новая задача, **создаётся** (`POST /issue`);
- **есть `jira_key`** → существующая задача, **обновляется** (`PUT /issue/{key}`).

Повторный прогон файлы из `done/` не трогает; файлы `ready: false` с ключом —
обновляет, дубли не создаются. Если отправка упала — файл остаётся как есть,
можно повторить.

**Сканирование исключает `*/done/**`.** Подпапки `done/` внутри эпик-папок при
обходе пропускаются целиком — обработанные задачи повторно не подхватываются.
Исключение действует **только для поиска задач на создание**; для резолва
локальных ссылок `links` содержимое `done/` (ключи блокеров) наоборот читается
(см. §7).

### Зачем хранить id (редактирование задачи)

Сохранённые `jira_key` / `jira_url` дают точную точку входа: чтобы отредактировать
задачу, не нужно искать её в JIRA — ключ берётся из front-matter файла (в `done/`,
из реестра или из черновика `ready: false`, оставшегося на месте). На этом и
построено обновление `ready: false`-черновиков по `jira_key` (`PUT /issue/{key}`).

Формат `index.json`:

```json
[
  {
    "file": "PROJ-855/done/C2-fix-excel-export.md",
    "epic": "PROJ-855",
    "jira_key": "PROJ-901",
    "jira_url": "https://jira.example.com/browse/PROJ-901",
    "summary": "Починить экспорт в Excel",
    "attachments": ["error.png"],
    "created_at": "2026-06-17T16:40:00+03:00"
  }
]
```

## 6. Инструменты MCP (tools)

| Tool | Назначение | Поведение |
|---|---|---|
| `list_markdown_tasks` | сканирует `TASKS_DIR`, отдаёт список `.md` с распарсенными project/summary/type/ready/epic | только чтение, ничего не создаёт |
| `create_jira_task` | создаёт/обновляет одну задачу из указанного файла | нет `jira_key` → создаёт; есть `jira_key` → обновляет (`PUT`). При `ready: true` и успехе — дописывает key и переносит в `done/` |
| `create_all_tasks` | проходит все `.md` в `TASKS_DIR` и заводит задачи пачкой | принимает `publish_unready: bool` (см. §5) — публиковать ли `ready: false`. При `false` пропускает `ready: false`; при `true` отправляет все. Файлы с `jira_key` обновляет, без — создаёт; `ready: true` переносит в `done/`, `ready: false` оставляет с ключом. Возвращает отчёт по каждому файлу |

Дополнительно (служебные, для безопасного старта):

| Tool | Назначение |
|---|---|
| `check_connection` | `GET /rest/api/2/myself` — проверка URL и токена |
| `dry_run` | парсит файлы и показывает, что **было бы** создано (включая проверку наличия/размера `attachments` и резолва `links`), без обращения к JIRA на запись |

## 7. Используемые эндпоинты JIRA REST API v2

| Метод | Эндпоинт | Зачем |
|---|---|---|
| `GET` | `/rest/api/2/myself` | проверка авторизации |
| `GET` | `/rest/api/2/field` | найти id поля с `name == "Epic Link"` → `JIRA_EPIC_FIELD` |
| `POST` | `/rest/api/2/issue` | создание задачи (файл без `jira_key`) |
| `PUT` | `/rest/api/2/issue/{key}` | обновление задачи (файл с `jira_key` вне `done/`, см. §5) |
| `POST` | `/rest/api/2/issue/{key}/attachments` | загрузка вложений (`attachments`) |
| `POST` | `/rest/api/2/issueLink` | создание связи `is blocked by` (`links`) |

**Вложения (`attachments`).** Грузятся **после** создания задачи, по одному
запросу на файл (или несколько полей `file` в одном multipart):

```
POST /rest/api/2/issue/PROJ-901/attachments
X-Atlassian-Token: no-check          # обязателен, иначе XSRF-отказ
Content-Type: multipart/form-data
  file=@<папка_задачи>/error.png
```

- Источник файлов — «папка задачи» (`<EPIC>/<имя_md_без_расширения>/`), пути
  берутся из поля `attachments` относительно этой папки.
- **Строгая проверка до создания задачи**: каждый файл существует и не превышает
  лимит размера вложения инстанса. Иначе задача **не создаётся**, ошибка в отчёт.
- «Папка задачи» — это директория, она не подхватывается сканером задач (ищутся
  только `.md`); в `done/` переезжает вместе с `.md` (см. §5).

**Картинки из тела (`![alt](pic.png)`).** На этапе подготовки описания:

1. В теле находятся markdown-картинки с **локальной** ссылкой (не `http(s)://`).
2. Файл `pic.png` из папки задачи добавляется в набор вложений (автоматически,
   без дублирования с `attachments`; те же строгие проверки наличия/размера).
3. Ссылка переписывается в JIRA-wiki по **имени файла**: `![alt](dir/pic.png)` →
   `!pic.png!`. JIRA отрисует вложение в описании по имени.
4. Имена картинок в пределах задачи должны быть **уникальны** (JIRA адресует
   вложение по имени, не по пути) — коллизия имён считается ошибкой задачи.
5. Внешние картинки (`http(s)://`) не загружаются и остаются ссылкой в тексте.

Связи создаются **после** создания задачи — по одной на каждый ключ из `links`.
Все связи одного типа: создаваемая задача **is blocked by** перечисленные.
Тело запроса (текущая задача `PROJ-901` заблокирована задачей `PROJ-900` из `links`):

```json
{
  "type": { "name": "Blocks" },
  "inwardIssue":  { "key": "PROJ-901" },
  "outwardIssue": { "key": "PROJ-900" }
}
```

Для типа `Blocks`: `outwardIssue` — «blocks», `inwardIssue` — «is blocked by».
Текущая задача всегда `inwardIssue`, блокер из `links` — `outwardIssue`.

**Резолв `links` в ключ `outwardIssue`:**

- Элемент вида `ABC-123` (буквы-дефис-число) → используется как **JIRA-ключ** как есть.
- Иначе элемент трактуется как **локальная ссылка** (префикс файла из той же
  эпик-папки). Ключ блокера ищется по двум источникам (в порядке приоритета):
  1. **Карта «префикс → ключ» текущего прогона** — если блокер создан только что
     в этом же запуске (он уже уехал в `done/`, но ключ запомнен в памяти).
  2. **`done/` соответствующей эпик-папки** — если блокер завели в **прошлый**
     прогон. Резолвер сканирует `TASKS_DIR/<EPIC>/done/`, находит файл с нужным
     префиксом и читает его `jira_key` (быстрый путь — через реестр
     `index.json`, где есть и путь файла с префиксом, и `jira_key`).
- Важно: исключение `*/done/**` касается только **поиска задач для создания**.
  Для **резолва ссылок** `done/` наоборот читается — там лежат уже заведённые
  блокеры с их ключами.
- Если локальная ссылка не разрешается (нет такого файла ни среди новых, ни в
  `done/`; блокер `ready: false`; его создание упало) — зависимая задача
  **не создаётся**, в отчёт пишется ошибка.

> Точное имя типа связи (`Blocks`) подтвердить на инстансе через
> `GET /rest/api/2/issueLinkType`.

Тело запроса на создание:

```json
{
  "fields": {
    "project":    { "key": "MAS" },
    "summary":    "Заголовок из markdown",
    "description": "Тело из markdown",
    "issuetype":  { "name": "Task" },
    "labels":     ["reports", "export"],
    "customfield_10008": "DEMO-100"
  }
}
```

Источники полей: `project.key` — из поля `project` файла; `summary`, `issuetype.name`
(`type`), `labels` — из front-matter; `customfield_10008` (это `JIRA_EPIC_FIELD`,
Epic Link) = ключ эпика из имени папки; `priority` не шлём — проектное значение
по умолчанию (`Medium`).

**Префикс `WIP: ` в `summary`** (см. §5): при создании с `ready: false` в
отправляемый `summary` добавляется `WIP: ` (`"summary": "WIP: <summary>"`); при
обновлении (`PUT`) с `ready: true` префикс `WIP: ` снимается. В самом файле
`summary` хранится без префикса.

## 10. Сценарий работы

1. Пользователь кладёт `.md`-файлы в папку эпика `TASKS_DIR/<EPIC>/`
   (имя папки = ключ эпика, напр. `PROJ-855`).
2. `check_connection` — убедиться, что токен/URL рабочие.
3. (один раз) определить `JIRA_EPIC_FIELD` через `GET /field`, записать в конфиг.
4. `dry_run` — посмотреть, что будет создано.
5. `create_all_tasks` — перед запуском сервер **спрашивает**, публиковать ли
   `ready: false` (`publish_unready`). При «нет» обрабатываются только
   `ready: true`; при «да» — все задачи. Файлы сортируются по
   **буквенно-числовому префиксу** имени (`B1`, `C1`, `C2`…) — это и есть порядок
   заведения: блокер создаётся раньше, его ключ кладётся в карту «префикс → ключ».
   При создании зависимой задачи локальные ссылки из `links` резолвятся в ключи
   по этой карте, связи `is blocked by` заводятся в JIRA. Файлы из `attachments`
   загружаются в задачу. Для каждого файла: нет `jira_key` → **создаётся**
   (`POST`), есть → **обновляется** (`PUT`). Каждый успешный файл получает
   `jira_key`; `ready: true` уезжает в `done/` (вместе с папкой задачи),
   `ready: false` остаётся на месте с ключом — следующий прогон его обновит.
6. Отчёт: по каждому файлу — created `KEY` / updated `KEY` / skipped (not ready) /
   skipped (done) / error.

## 11. Регистрация в Claude Code

```bash
claude mcp add jira-tasks -- /path/to/your-project/go-jira-mcp/bin/server
```

Env-переменные (`JIRA_URL`, `JIRA_PERSONAL_ACCESS_TOKEN`, ...) передаются серверу
через конфиг MCP или окружение запуска.

## 12. Вне рамок (на будущее)

- Комментарии к задачам.
- Подзадачи и иерархия глубже «эпик → задача».
- Полная конвертация markdown → wiki-markup. Сейчас описание передаётся как есть,
  переписываются **только картинки** (`![](pic.png)` → `!pic.png!`, см. §7);
  заголовки, списки, ссылки и пр. не конвертируются.

## 13. Открытые вопросы

- Точный id поля «Epic Link» (`JIRA_EPIC_FIELD`) — определить на инстансе.
- Ключи проектов — задаются полем `project` в каждом файле; эпики — именами папок.
- Набор допустимых `issuetype` в проекте (Task / Bug / Story) — сверить с JIRA.
- Точное имя типа связи `Blocks` (`GET /rest/api/2/issueLinkType`) — подтвердить.
- Поведение при невалидном/отсутствующем префиксе имени файла (`B1`, `C1`…) —
  считать ошибкой и пропускать с сообщением в отчёте.
- Лимит размера вложений инстанса — узнать (по умолчанию ~10 МБ) или читать из
  `GET /rest/api/2/serverInfo`/конфигурации; для проверки `attachments` в `dry_run`.
- Опция управления размером картинки в wiki (`!pic.png|width=600!`/`thumbnail`) —
  пока вставляем как `!pic.png!`; синтаксис размера — на будущее.
- Резолв локальных ссылок `links` (префикс → ключ) опирается на порядок по
  префиксу: блокер должен иметь меньший префикс. Ссылка «вперёд» (на больший
  префикс) или на `ready: false` — ошибка, зависимая задача не создаётся.
