# Гайдлайны профиля <имя профиля>

**Это скелет.** Заменить содержимое на правила своей команды, а этот файл — на индекс
получившегося. Пояснения ниже про устройство, а не про стек: их стоит сохранить.

Гайдлайны — **источник правды** по контрактам, миграциям, типам и авторизации, и
единственное, что отличает ваш профиль от чужого с тем же стеком. Агенты пайплайна
сверяются с ними начиная с **шага 3 (Импакт-Аналитик)** и далее везде, где это применимо
(блоки «Правила профиля» в шагах ядра).

Ядро ссылается на **роли** из `profile.yaml` (`api_spec`, `migrations`, `data_types`,
`auth`, `db_schema_style`), а не на имена файлов: имена — ваше дело, роли — контракт с ядром.

## Как писать гайдлайн

Работающий гайдлайн отвечает на три вопроса, и в этом порядке:

1. **Что делать** — правило в повелительном наклонении, без «желательно» и «по возможности».
   Агент не умеет взвешивать пожелания: правило либо проверяемо, либо его нет.
2. **Почему** — один-два факта, из которых правило следует. Без них агент «оптимизирует»
   правило при первом же конфликте.
3. **Чек-лист** в конце — по пункту на правило. Это машиночитаемая поверхность, по которой
   сверяются шаги 7a и 9; проза выше него для человека, чек-лист — для прогона.

Чего избегать: пересказа документации инструмента (она есть у агента), пересказа файла
конвенций проекта (`AGENTS.md` — два источника разъедутся молча) и правил, нарушение
которых нельзя увидеть в диффе.

## Приоритет

При конфликте источников:
**`AGENTS.md` проекта → гайдлайны профиля → ядро → персональные предпочтения агента.**

## Как это выглядит заполненным

Так выглядит блок «Файлы» в заполненном профиле (демо-стек: FastAPI + SQLAlchemy +
Alembic, PostgreSQL). В каждом файле гайдлайнов этого шаблона есть свой раздел
«Как это выглядит заполненным» с примером правил.

| Файл | Роль в `profile.yaml` | О чём | Где применяется |
|------|------|-------|------------------|
| [01-migrations.md](./01-migrations.md) | `migrations` | Alembic: одна ревизия = один файл, обратимость, явная схема, `concurrently` для индексов | Шаги 3, 6 |
| [02-api-contract.md](./02-api-contract.md) | `api_spec` | `openapi.json` из кода, набор методов, единое тело ошибки `{"error": {...}}`, `extra="forbid"` | Шаги 3, 5, 7, 9 |
| [03-data-types.md](./03-data-types.md) | `data_types` | `BIGINT`/`NUMERIC` строкой наружу, `TIMESTAMPTZ` в UTC, одна пустота на смысл | Шаги 3, 5, 6, 8 |
| [04-auth.md](./04-auth.md) | `auth` | аутентификация в middleware, право — в `Depends(require(...))`, в бизнес-логике проверок нет | Шаги 3, 5, 8 |
| [05-db-schema-style.md](./05-db-schema-style.md) | `db_schema_style` | `GENERATED ALWAYS AS IDENTITY`, `COMMENT ON`, нейминг индексов, обязательные `GRANT` | Шаги 3, 6, 9 |
