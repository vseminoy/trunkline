# profiles/ — профили стека

Ядро (`core/`) не знает ни одного языка, инструмента и команды. Всё это живёт здесь.
Один профиль = один технологический стек.

```
profiles/<имя>/
├── profile.yaml     ← манифест: слоты, из которых ядро берёт стек-специфику
├── guidelines/      ← обязательные правила стека (источник правды, версионируется отдельно)
├── steps/           ← надстройки шагов: NN-*.md, объявляются в step_overlays
├── tasks/           ← аналитическая ветка: соглашения по оформлению задач,
│                      настройка издателя (объявляются в секции `tasks`)
└── hooks/           ← скрипты машинных гейтов (pre-commit и т.п.)
```

Рядом, вне профилей, лежит `publishers/<издатель>/` — контракты инструментов заведения
задач. Они принадлежат инструментам, а не профилям: профиль ссылается на контракт
слотом `tasks.publisher.contract`, а свои соглашения держит в `tasks/`.

Готовые профили:

| Профиль | Стек |
|---|---|
| [`oss-py-fastapi`](./oss-py-fastapi/) | Python, FastAPI + Pydantic v2, aiosql, Alembic, PostgreSQL+PostGIS |
| [`example-stack`](./example-stack/) | шаблон — не стек, а каркас с плейсхолдерами для написания своего профиля |

Имя профиля начинается с организации-владельца гайдлайнов (напр. `acme-`): гайдлайны — это
**чьи-то** стандарты, а не свойство стека. Два разных Go+Echo профиля с разными
правилами по типам и авторизации — нормальная ситуация, и различать их надо по владельцу.
Гайдлайнов без конкретного владельца (общепринятые практики экосистемы, а не чей-то
внутренний стандарт) — префикс `oss-`.

## Как подключается

В `AGENTS.md` разрабатываемого проекта:

```markdown
## Pipeline flags
- profile: oss-py-fastapi
- knowledge: .pipeline/knowledge
```

Профиль не объявлен → агент останавливается и спрашивает. Угадывание запрещено:
неверный профиль молча отключает часть сверок.

Остальные флаги (`knowledge`, `metrics` и прочие) — в `SETUP.md`.

## Как написать свой профиль

1. Скопировать каталог `example-stack/` под своим именем и заполнить слоты
   манифеста под свой стек. Слот, которого в стеке нет, оставить `null` —
   опирающиеся на него блоки шагов объявят «не применимо».

   **Пути внутри манифеста даны от каталога профиля** (`guidelines/README.md`,
   `steps/07-tester.md`, `hooks/pre-commit-gate.sh`), поэтому копия работает сразу —
   ей нечего переписывать, кроме содержимого. Путь, который называет профиль внутри
   себя (`profiles/<имя>/guidelines/…`), запрещён и отбивается линтером: в копии он
   продолжает указывать на оригинал, а такая копия молча читает чужие гайдлайны.

   Имя в манифесте (`name:`) обязано совпадать с именем каталога — по нему профиль
   адресуют флаг `profile:`, `trunkline profile add` и вендоринг.

   Исключение — `tasks.*` (п. 5): эти пути указывают за пределы профиля.
2. `required_project_files` — что должно лежать в проекте, чтобы пайплайн вообще
   стартовал. Единственный файл, обязательный независимо от профиля, — `AGENTS.md`
   (в нём живут флаги), и его требует ядро. Всё остальное — ваше решение: файл конвенций,
   конфиг линтера, что угодно. Список пустой — тоже допустимо.
3. `guidelines/` — свои правила по контрактам, миграциям, типам, авторизации,
   стилю схемы. Роли в манифесте (`api_spec`, `migrations`, `data_types`, `auth`,
   `db_schema_style`) — то, чем оперирует ядро; имена файлов — ваше дело.
   Гайдлайнов может не быть вовсе: тогда блоки сверки объявляются «не применимо».
4. `steps/NN-*.md` — надстройки **только там, где стек реально что-то добавляет**.
   Надстройка уточняет шаг, а не переписывает: при конфликте с ядром выигрывает ядро.
   Пустых надстроек не заводить — лишний файл в контексте дороже, чем его отсутствие.
5. `tasks` — трекер задач для аналитической ветки: `format_spec` (единый источник правды
   по формату задач), `dir` (корень задач, подпапка = ключ эпика), `analysis_dir`
   (состояние анализа) и `publisher` (`name`, `setup`, `operations.pull` / `.dry_run` /
   `.publish`). Ядро оперирует только этими слотами и не знает имени инструмента.
   Секция `null` — допустимо: аналитик тогда складывает `.md` в названную пользователем
   папку и на этом останавливается, шаги публикации объявляются «не применимо».

   **Здесь три якоря.** `format_spec` и `publisher.setup` — документы профиля (путь от
   каталога профиля): они едут в проект вместе с профилем, поэтому доступны там.
   `dir` и `analysis_dir` — данные разрабатываемого проекта (путь от корня проекта).
   `publisher.contract` — документ
   **инструмента** (путь от корня пайплайна, `publishers/<издатель>/…`). Спека формата,
   лежащая в каталоге вашего инструмента, а не в профиле, в установленный проект не
   попадёт — и аналитик встанет на первом же шаге. Линтер проверяет все три.

   **Где живут задачи: две рабочие раскладки.** `dir` и `analysis_dir` — единственные
   слоты, которым разрешено выйти за пределы проекта (`../`). Абсолютный путь запрещён:
   он не переезжает между машинами.

   ```yaml
   # A. В проекте (по умолчанию). Анализ коммитится вместе с кодом.
   dir: .pipeline/tasks/
   analysis_dir: .pipeline/tasks/_analysis/

   # B. В отдельном репозитории — соседний клон или подмодуль.
   dir: ../analysis/tasks/
   analysis_dir: ../analysis/tasks/_analysis/
   ```

   Смысл B в том, что состояние анализа обновляется **на каждом шаге** аналитика, и в
   истории кода это шум; у базы знаний того же не происходит — шаг 20 пишет один коммит
   на прогон, поэтому она остаётся в репозитории сервиса. Аналитик при обеих раскладках
   работает **внутри** проекта: ему нужны код, флаги из `AGENTS.md` и `required_project_files`,
   а «read-only with respect to the project code» означает, что код рядом, просто его
   нельзя менять. Меняется только то, куда он пишет.

   Цена B — путь через границу репозиториев git ничем не подкреплён: клонировали один
   репозиторий из двух, и шаг 1 разработчика не увидит, какие требования эпика
   ушли в другие задачи, — граница этой задачи станет догадкой. Поэтому `init` такой каталог **не создаёт**
   (он чужой), а `trunkline doctor` проверяет, что он существует и непуст, — пустой
   каталог неотличим от неинициализированного подмодуля и означает то же самое.

   **Формат задач — два документа, а не один.** Контракт издателя
   (`publisher.contract`) описывает то, что проверяет код инструмента: имена полей,
   размещение файлов, поведение при ошибке. Он принадлежит инструменту, лежит
   в `publishers/` и общий для всех профилей, объявивших этого издателя. Ваш
   `format_spec` описывает только соглашения команды — что писать внутри полей — и
   ссылается на контракт, а не пересказывает его. Граница проходит по тому, кто ловит
   нарушение: контракт — код, отказом в заведении; соглашения — ревью.

   Объявлена секция `tasks` → `trunkline init` кладёт в проект вторую точку входа
   (`/trunkline-analytic`) и создаёт `<dir>`. Не объявлена → ни того, ни другого.
6. Прогнать `python3 scripts/lint-core-profile-boundary.py` — он проверит, что все
   слоты, на которые ссылается ядро, в вашем манифесте объявлены, а пути существуют.
7. Прогнать `node scripts/run-own-evals.js` и одну живую задачу по полному маршруту
   `feature` — до шага 20.

## Правило границы

Если правку тянет внести в `core/`, а звучит она как «у нас в Go принято…» — она
не в ядро, а в профиль. Обратное тоже верно: механика, которая сработает на любом
стеке (трассируемость `R-<прогон>-<n>`, сверка 7a, журнал прогонов), в профиль не спускается.
