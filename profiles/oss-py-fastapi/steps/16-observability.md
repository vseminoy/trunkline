# Надстройка профиля oss-py-fastapi — шаг 16 (Наблюдаемость)

Читать сразу после `core/developer/steps/16-observability.md`.

- Логирование — структурированное, по `09-logging.md` (`structlog` поверх stdlib,
  аналог `slog`). Первый аргумент — стабильное имя события (`route_replan_failed`),
  данные — именованными полями (`log.info("osrm_request_finished", status=200,
  duration_ms=412)`), не интерполяцией в текст.
- Данные, по которым потом ищут (id заявки, id бригады, код ответа OSRM), кладутся
  в поля, а не в текст сообщения. Идентификатор долгой операции (`run_id`) привязывается
  через `bind_contextvars` один раз, а не передаётся в каждый вызов.
- Проверка записей в тестах — `structlog.testing.capture_logs()`, по событию и полям.
- Границы, которые логируются всегда:
  - вызов OSRM (`/table`, `/route`) — URL без секретов, код ответа, длительность;
  - решение OR-Tools — статус (`OPTIMAL`/`FEASIBLE`/`INFEASIBLE`), длительность
    решения, число неназначенных заявок (`AddDisjunction`);
  - HTTP-запросы FastAPI — метод, шаблон пути, код ответа, длительность, `request_id`
    (middleware; access-лог uvicorn выключен, чтобы не было дублей).
- В логи не попадают токены, пароли, JWT целиком (только субъект/роль из payload).
- Проверка после изменений: `commands.build` (`mypy src`) и `commands.test_unit`.
