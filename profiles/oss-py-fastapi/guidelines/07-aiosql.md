# 07. Доступ к данным (aiosql)

Роль `db_access` (не спрашивается ядром — используется собственными надстройками
шагов профиля, шаги 3, 6, 8).

**Организация файлов.** Один `.sql`-файл на агрегат/домен (`queries/requests.sql`,
`queries/engineers.sql`, `queries/routes.sql`), а не один файл на всё приложение —
иначе конфликты слияния гарантированы на любом одновременном изменении. Именованный
запрос — блок с маркером `-- name: <имя><суффикс>`:

| Суффикс | Значение | Пример |
|---|---|---|
| (нет) | много строк | `-- name: list_pending_requests` |
| `^` | одна строка или `None` | `-- name: get_engineer^` |
| `$` | одно скалярное значение | `-- name: count_pending_requests$` |
| `!` | выполнить, без результата (`INSERT`/`UPDATE`/`DELETE`) | `-- name: assign_engineer!` |
| `<!` | выполнить и вернуть сгенерированный id | `-- name: create_request<!` |

**Параметры — только именованные.** `:request_id`, не позиционные `?`/`%s` и не
f-string/конкатенация значения в текст запроса — конкатенация означает SQL-инъекцию
при первом же пользовательском вводе (см. `09-10-critic-security.md`).

**В SQL — запрос, не бизнес-правило.** Джойны и агрегации — да (это работа БД).
Ветвление бизнес-логики (какая заявка кому назначена, штраф за неназначенность) —
нет: это работа сервиса и модели OR-Tools, а не SQL. Запрос с `CASE`, реализующим
доменное правило, а не просто форматирование колонки, — повод перенести правило в
сервис.

**Репозиторий — тонкая обёртка, а не сквозной проброс.** Репозиторий получает
объект `queries` (результат `aiosql.from_path(...)`) и соединение через `Depends(...)`,
вызывает именованный метод и **обязан** собрать результат в Pydantic-модель до возврата
(см. `03-data-types.md` — граница репозитория). Транзакции — явные (`with conn:` /
`conn.begin()`), не полагаться на автокоммит `psycopg` по умолчанию.

**N+1.** Список сущностей с зависимыми данными (заявки с их назначенной бригадой)
получается одним запросом с `JOIN`, а не циклом «получить список → получить бригаду
для каждой». Цикл вызовов `queries.get_engineer^` внутри цикла по списку заявок —
дефект, который ловит только чтение кода (см. критик, `09-10-critic-security.md`),
инструмент это не проверяет.

## Чек-лист

- [ ] Один `.sql`-файл на агрегат, не общий файл на всё приложение.
- [ ] Все параметры — именованные, конкатенации значения в текст запроса нет.
- [ ] SQL не содержит доменного ветвления сверх агрегации/джойна.
- [ ] Результат aiosql-запроса не пересекает границу репозитория не будучи Pydantic-моделью.
- [ ] Список с зависимыми данными — один запрос с `JOIN`, не цикл запросов.
