# 02. Контракт API

Роль `api_spec`. Читают шаги 3, 5 (спецификация), 7 (тесты), 9 (критик).

**Где живёт контракт.** Контракт — файлы `openapi/` (корень `openapi/openapi.yaml`,
общие компоненты `openapi/common.yaml`), и он **пишется до
кода**: шаг 5 (Спецификатор) утверждает его как часть спецификации задачи, шаг 8
(Генератор) реализует код, соответствующий уже утверждённому файлу, а не наоборот.
Спека — не производная реализации: изменение контракта начинается с правки
`openapi.yaml`, а не с правки Pydantic-модели в коде с последующей пересборкой json.
Из спеки шаг 8 генерирует Pydantic-модели запроса/ответа
(`datamodel-code-generator`, `stack.contract.codegen`) — что именно генерируется
и что поэтому нельзя писать руками, см. [08-generated-code.md](./08-generated-code.md).

**Роуты остаются рукописными.** Генератора, который безопасно совмещал бы
сгенерированный по спеке роутинг с DI FastAPI (аутентификация, сессия БД, сервис),
в экосистеме нет: по спеке генерируются только схемы данных, а не серверный
интерфейс целиком. Поэтому соответствие реализации спеке (путь, метод, коды ответов,
формы ошибок) не гарантировано компилятором и генератором — оно проверяется
**контрактными тестами** (`schemathesis`, см. `steps/07-tester.md`): тест-кейсы
строятся автоматически из `openapi.yaml` и прогоняются против поднятого приложения.
Расхождение реализации со спекой — падение контрактного теста, а не повод
скорректировать спеку постфактум под то, что уже написано.

**Методы.** Наружу отдаются `GET`, `POST`, `PATCH`, `DELETE`. `PUT` не используется:
частичное обновление везде идёт через `PATCH`, и две семантики обновления на один
ресурс путают клиентов (фронт на React, внешнюю интеграцию — если она есть).

**Коды ответов и ошибки** — по `10-errors.md`: тело есть только у `400` (схема
`ValidationError` — `message` либо список `fields` «параметр + ошибка»), все остальные
коды ошибок отдаются без тела, и текст для пользователя по коду формирует клиент;
`422` не используется. Ответ ошибки формирует единый обработчик
(`app.add_exception_handler(...)`), а не маршрут.

**Файлы спеки.** Контракт — несколько файлов в `openapi/`, связанных `$ref`:

- `openapi/common.yaml` — **только** `components`, общие для всех операций: схемы
  ошибки `ValidationError` и `FieldError`, ответы (`BadRequest` с телом; `NotFound`,
  `Conflict`, `PayloadTooLarge`, `ServiceUnavailable`, `InternalError` без тела —
  `10-errors.md`), заголовок `X-Request-ID`, общие параметры (пагинация и т.п.). Путей
  в нём нет.
- `openapi/openapi.yaml` — корневой документ (`info`, `paths`, `servers`) и схемы
  предметной области; при росте API пути выносятся в файлы по ресурсам
  (`openapi/paths/<ресурс>.yaml`), корень ссылается на них.

Схема ошибки и ответы ошибок описываются **только** в `common.yaml`; каждая операция
ссылается на них (`$ref: "./common.yaml#/components/responses/BadRequest"`), копия или
своя схема ошибки в другом файле запрещена. Инструменты читают многофайловую спеку от
корня: `datamodel-codegen --input openapi/openapi.yaml`, `schemathesis` — по пути к
корню, генератор клиента на фронтенде — тоже; ручная склейка в один файл не нужна.

**Схемы.** Общие структуры выносятся в `components.schemas` и переиспользуются
(`$ref`), а не копируются между операциями. У каждого поля — `description` (единицы
измерения обязательны там, где значение без них неоднозначно: секунды vs минуты, метры
vs километры). `operationId` задаётся явно в стиле `snake_case` глагол+сущность
(`assign_engineer`, `replan_route`) — генератор и клиент используют его как имя
метода/функции. `response_model` на роуте — сгенерированная по спеке схема, эндпоинт,
отдающий голый `dict` или произвольный `JSONResponse` без неё, не проходит шаг 9.

**`additionalProperties: false` — на каждой схеме-объекте**, во всех файлах, включая
вложенные объекты и схемы ответов. Генератор транслирует его в
`model_config = ConfigDict(extra="forbid")`: лишнее или опечатанное поле запроса
отбивается `400`, а не игнорируется молча; лишнее поле ответа ломает тест, а не
утекает клиенту.

**Ограничения на входные данные — строго и полностью.** Спека — единственное место,
где записаны правила допустимого ввода: по ней валидирует backend (сгенерированные
модели) и фронтенд (схемы валидации формы, сгенерированные из той же спеки). Правило,
которого нет в спеке, не проверит ни один из них. Для каждого свойства схемы запроса и
каждого параметра (`query`, `path`, поля `multipart/form-data`):

| Тип | Обязательно | Когда применимо |
|---|---|---|
| `string` | `maxLength`; `minLength: 1`, если пустая строка недопустима | `pattern` — у строк с известным форматом (коды, идентификаторы, телефоны); `format` (`date`, `date-time`, `uuid`, `email`); `enum` — у закрытого набора значений |
| `integer`, `number` | `minimum` и `maximum` | `exclusiveMinimum`/`exclusiveMaximum`, `multipleOf` |
| `array` | `maxItems`; `minItems`, если пустой массив недопустим | `uniqueItems: true`, если повторы бессмысленны |
| `object` | `additionalProperties: false`; `required` — явный список | — |
| файл (`format: binary`) | предельный размер — в `description` операции | — |

- Граница без ограничения — это решение, а не пропуск: строка, длина которой
  действительно не ограничена, получает `maxLength` по предельному размеру запроса и
  комментарий почему.
- `pattern` — в общем подмножестве регулярных выражений ECMA-262 (фронтенд) и Rust
  `regex` (Pydantic v2): без lookahead/lookbehind и обратных ссылок, с якорями `^…$`.
- Схемы ответов ограничений длины не требуют — их данные формирует сервер.

**Предельный размер запроса ограничен на backend.** Проверка размера файла на клиенте —
удобство, а не защита: запрос можно отправить в обход формы. Поэтому:
- ASGI-middleware (чистая ASGI, не `BaseHTTPMiddleware`) отклоняет тело больше
  `MAX_REQUEST_BODY_BYTES` (настройка `pydantic-settings`) ответом `413` без тела: сразу —
  по заголовку `Content-Length`, а без него (chunked) — считая байты по мере чтения и
  прерывая приём на превышении. Тело не буферизуется целиком до проверки.
- Предел один на приложение и равен самому большому допустимому запросу (обычно —
  загрузке файла); JSON-операции дополнительно ограничены `maxLength`/`maxItems` своих
  схем. Операции, которым нужен меньший предел, проверяют его сами (размер загруженного
  файла) и отвечают тем же `413`.
- `multipart/form-data` разбирается с явными пределами Starlette
  (`request.form(max_files=..., max_fields=..., max_part_size=...)`), а не с настройками
  по умолчанию.
- Обратный прокси перед backend (nginx на стенде) ставит тот же предел
  (`client_max_body_size`) — как первую линию, не вместо middleware: backend бывает
  доступен и напрямую.
- В спеке у каждой операции с телом запроса объявлен
  `"413": {$ref: "./common.yaml#/components/responses/PayloadTooLarge"}`, а предел в
  байтах назван в `description` операции загрузки — фронтенд берёт его оттуда.

**Валидация входных данных — без кода в контроллере.** Отдельная middleware,
проверяющая запросы по спеке, не пишется: проверку уже делает FastAPI по
сгенерированным моделям, до вызова обработчика. Генератор переносит ограничения спеки
в `Field(...)` (`min_length`, `max_length`, `pattern`, `ge`/`le`, `min_length` у
списков), FastAPI отклоняет запрос с `RequestValidationError`, единый обработчик
(`10-errors.md`) превращает её в `400` с `fields`. Вторая валидация по той же спеке
(openapi-core и т.п.) дала бы два источника ошибок разного формата и двойную стоимость
на каждый запрос.
Одна точка, где спека и код могут разойтись: параметры `query`/`path`/формы задаются в
сигнатуре рукописного роута (`Query(max_length=...)`), а не генерируются. Это
удерживает контрактный тест: `schemathesis` в негативном режиме генерирует значения,
нарушающие ограничения спеки, и требует `400` — роут, забывший ограничение, падает на
этом тесте (`steps/07-tester.md`).

Бизнес-проверки, которые спекой не выражаются (окно начала раньше окончания, регион
заявки совпадает с регионом бригады, содержимое загруженного файла), делает `service`
и поднимает `InvalidInput` — ответ тот же `400` (`10-errors.md`).

**Версионирование.** Публичные роуты — под префиксом `/api/v1`. Смена формы ответа —
новая версия префикса в спеке, не расширение старой опциональными полями «на всякий
случай».

**Долгие операции (пересчёт плана, солвер).** Эндпоинт, который может не уложиться
в обычный таймаут запроса (полный пересчёт VRPTW-плана), фиксирует выбор **в спеке**
на шаге 5: либо документированный таймаут в `description`, либо `202 Accepted` с
идентификатором задачи и отдельная операция опроса статуса — не решается на шаге 8
по вкусу исполнителя.

## Чек-лист

- [ ] Правка контракта начата в `openapi/`, а не в коде.
- [ ] Каждая операция имеет `operationId` и схему ответа для каждого кода.
- [ ] Коды в спеке совпадают с тем, что реально возвращает код (проверено `schemathesis`).
- [ ] Схема ошибки и ответы ошибок — только в `openapi/common.yaml`; операции ссылаются на них, копий нет.
- [ ] Ошибки — по `10-errors.md`: у операций с входными данными `400` через `$ref` на `common.yaml#/components/responses/BadRequest`, у остальных кодов ошибок нет `content`.
- [ ] `additionalProperties: false` на каждой схеме-объекте, включая вложенные и схемы ответов.
- [ ] У каждой строки входа — `maxLength` (и `minLength`/`pattern`/`format`/`enum`, где применимо), у чисел — `minimum`/`maximum`, у массивов — `maxItems`; `pattern` без lookaround и обратных ссылок.
- [ ] Ограничения параметров `query`/`path`/формы в сигнатуре роута совпадают со спекой (негативный прогон `schemathesis`).
- [ ] Размер тела ограничен middleware (`MAX_REQUEST_BODY_BYTES` → `413` без тела); у операций с телом объявлен `413`.
- [ ] У каждого поля — `description`, единицы измерения названы явно.
- [ ] Pydantic-схемы в `src/api/schemas/generated/` не редактировались руками (`08-generated-code.md`).
- [ ] Типы полей — по [03-data-types.md](./03-data-types.md).
