# 10. Ошибки: ответ клиенту и логирование

Роль `errors` (не спрашивается ядром — используется надстройками шагов профиля, шаги 5,
7, 7a, 8, 9). Логирование в целом — `09-logging.md`; здесь — только то, что касается
ошибок.

Один принцип для всех операций API, без исключений:

1. **Только `400` имеет тело.** Это ошибка входных данных, и сервер объясняет её текстом
   или по полям — клиенту нужно показать её пользователю у формы.
2. **Все остальные коды ошибок (`401`, `403`, `404`, `409`, `413`, `415`, `429`, `5xx`)
   отдаются без тела** (`Content-Length: 0`). Текст для пользователя формирует клиент по
   паре «операция + код ответа» — формулировки для людей живут в одном месте, на клиенте,
   а не размазаны между клиентом и сервером.
3. **Ошибка логируется там, где у неё есть смысл**: бизнес-ошибка — в обработчике
   маршрута с бизнес-параметрами; ошибка БД или внешнего сервиса — в месте возникновения
   с техническими деталями. Все записи одного запроса связаны его `request_id`.

## Тело `400`

Схема `ValidationError` — одна на всё API, объявлена в `openapi/common.yaml`
(`components.schemas.ValidationError` и `FieldError`); там же — ответы ошибок
(`components.responses`: `BadRequest` с телом, остальные без `content`) и заголовок
`X-Request-ID`. Другие файлы спеки только ссылаются на них (`02-api-contract.md`).
Ровно одно из двух полей:

```json
{"message": "Файл не содержит ни одной заявки"}
```

```json
{"fields": [
  {"name": "window_start", "message": "Начало окна позже его окончания"},
  {"name": "engineers[2].skills", "message": "Нужно от 1 до 3 навыков"}
]}
```

- `message` — ошибка запроса в целом, которую нельзя привязать к одному параметру.
- `fields` — ошибки конкретных входных параметров; клиент показывает каждую у своего поля.
  `name` — имя параметра **как в контракте** (поле тела, query- или path-параметр, без
  префиксов `body`/`query` из `loc` Pydantic); вложенность — через точку, индекс
  массива — в `[]`.
- Тексты — для человека, на языке продукта, без SQL, трассировок, имён классов,
  внутренних идентификаторов и ответов внешних сервисов. Встроенные сообщения Pydantic
  (английские, технические) клиенту не отдаются: обработчик переводит их по `type` ошибки
  (`missing`, `string_type`, `greater_than`, …) в текст продукта, неизвестный `type` —
  в общий «Некорректное значение».

В спеке у каждой операции, принимающей входные данные, объявлен ответ
`"400": {$ref: "./common.yaml#/components/responses/BadRequest"}`, а коды без тела —
ссылкой на соответствующий ответ из `common.yaml` (`NotFound`, `ServiceUnavailable`, …).

## Коды без тела

- **Код однозначен внутри операции.** Раз клиент строит текст по паре «операция + код»,
  один код одной операции означает ровно одну ситуацию. Если клиенту нужно различать две
  ситуации, у них разные коды — или это `400` с текстом. `description` ответа в спеке —
  та самая ситуация, по ней клиент и пишет свой текст.
- **`422` не используется.** Ошибку валидации запроса FastAPI/Pydantic
  (`RequestValidationError`) единый обработчик переводит в `400` с `fields`.
- **Ответы Starlette тоже без тела.** По умолчанию неизвестный путь и неразрешённый метод
  отдают `{"detail": "Not Found"}` — обработчик `StarletteHTTPException` отдаёт тот же код
  без тела.
- **`5xx`:** `503` — недоступна зависимость (БД, внешний сервис), запрос можно повторить;
  `500` — всё непредусмотренное.
- **У каждого ответа, включая ошибки, есть заголовок `X-Request-ID`.** Тела нет, но
  клиент может показать идентификатор для обращения в поддержку, а по нему находятся все
  записи лога этого запроса. Для `500` это требует отдельного внимания: обработчик
  `Exception` работает снаружи пользовательских middleware, поэтому заголовок он ставит
  сам, из `contextvars`.

## Как устроено в коде

- **Доменные исключения** — в `src/errors.py`, без знания об HTTP: базовый `AppError` и
  классы по смыслу (`InvalidInput(message=... | fields=[...])`, `NotFound`, `Conflict`,
  `DependencyUnavailable`); доменные — их наследники с именем по бизнесу
  (`PlanNotFound(NotFound)`). У исключения есть `reason` (стабильный `snake_case`) и
  `params` — бизнес-параметры для лога.
- **Сопоставление с HTTP** — в `src/api/errors.py`: таблица «класс исключения → код» и
  обработчики, зарегистрированные через `app.add_exception_handler(...)`. Ответ клиенту
  формирует только этот модуль; маршрут ответ ошибки сам не собирает.
- **Сервис и репозиторий `HTTPException` не бросают** — это HTTP-слой.

## Логирование ошибок

**Бизнес-ошибка — в обработчике маршрута.** Маршрут ловит доменные ошибки своей операции,
пишет одну запись о том, **что не удалось с точки зрения бизнеса и с какими
параметрами**, и пробрасывает исключение дальше — ответ формирует единый обработчик:

```python
@router.post("/plan/build")
async def build_plan(req: BuildPlanRequest, service: PlanServiceDep) -> PlanResponse:
    try:
        return await service.build(region=req.region, date=req.date)
    except AppError as e:
        log.warning("plan_build_failed", reason=e.reason, region=req.region,
                    date=req.date, **e.params)
        raise
```

- Имя события — `<операция>_failed`; поля — `reason` и бизнес-параметры запроса
  (идентификаторы, регион, тип события), не тело запроса целиком и не персональные данные.
- Уровень: ошибка клиента (`4xx`) — `warning`, ошибка сервера или зависимости (`5xx`) —
  `error`.
- `try/except` в маршруте служит **только для этой записи** и всегда заканчивается
  `raise`: он не глотает ошибку и не собирает ответ.

**Ошибка БД или внешнего сервиса — в месте возникновения.** Репозиторий и HTTP-клиент
пишут техническую запись там, где поймали исключение драйвера или сети, и поднимают
доменное исключение с цепочкой причин:

```python
except httpx.HTTPError as e:
    log.error("osrm_request_failed", endpoint="table", profile=profile,
              duration_ms=elapsed_ms, exc_info=True)
    raise DependencyUnavailable(reason="osrm_unavailable") from e
```

- Поля — то, что нужно для разбора: имя запроса aiosql и `sqlstate` для БД; эндпоинт,
  код ответа и длительность для внешнего сервиса. Параметров запроса с персональными
  данными и строк подключения здесь тоже нет.
- Выше по стеку та же техническая ошибка повторно не логируется — только бизнес-запись
  маршрута, у неё другое событие и другой смысл.
- Для репозиториев это одна обёртка вокруг вызова aiosql, а не `try/except` в каждой
  функции.

**Связь записей.** HTTP-middleware (`09-logging.md`) привязывает `request_id` через
`bind_contextvars`, долгая операция — ещё и `run_id`. Поэтому поиск по одному
`request_id` даёт цепочку: `db_query_failed` → `plan_build_failed` →
`http_request_finished status=503`. Код, выносимый в поток (солвер), запускается через
`anyio.to_thread.run_sync`/`asyncio.to_thread`, которые копируют контекст;
голый `run_in_executor` контекст теряет.

**Остальное — в едином обработчике.** Он пишет запись только о том, чего никто не
залогировал раньше:
- `request_validation_failed` — ошибка валидации до входа в маршрут: путь-шаблон и
  **имена** невалидных полей, без значений (в значениях могут быть персональные данные);
- `unhandled_error` — непредусмотренное исключение, `log.exception(...)` со стеком,
  ответ `500`.

## Тесты

- На каждый код ошибки, объявленный у операции: код ответа; для `400` — тело по схеме
  `ValidationError` (`message` или `fields` с именами из контракта); для остальных —
  пустое тело; заголовок `X-Request-ID` есть.
- Через `structlog.testing.capture_logs()`: бизнес-ошибка даёт запись `<операция>_failed`
  с `reason` и бизнес-параметрами; ошибка зависимости даёт две записи (место
  возникновения + маршрут) с одним и тем же `request_id`.
- `schemathesis` ловит `422` или тело у кода без тела как расхождение со спекой.

## Чек-лист

- [ ] Тело есть только у `400`, по схеме `ValidationError` (`message` либо `fields`).
- [ ] Остальные коды ошибок — без тела; `422` и `{"detail": ...}` Starlette не отдаются.
- [ ] Код ошибки однозначен внутри операции; ситуация описана в `description` ответа в спеке.
- [ ] У каждого ответа, включая `500`, есть `X-Request-ID`.
- [ ] Маршрут логирует бизнес-ошибку `<операция>_failed` с `reason` и параметрами и
      пробрасывает её дальше; ответ собирает только `src/api/errors.py`.
- [ ] Ошибки БД и внешних сервисов логируются в месте возникновения и поднимаются
      доменным исключением `from e`; повторно выше не логируются.
- [ ] В текстах `400` и в логах нет SQL, трассировок в тексте, секретов и персональных данных.
