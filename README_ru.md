# trunkline

[![License: Polyform Noncommercial 1.0.0](https://img.shields.io/badge/license-Polyform%20Noncommercial%201.0.0-blue.svg)](LICENSE)

**Spec-driven development (SDD) пайплайн для AI-агентов, заточенный под brownfield — и CLI,
который устанавливает его в ваш проект.**

На английском: [`README.md`](README.md). Подробная презентация (слайды) с разбором всей механики:
[`trunkline-overview.ru.html`](trunkline-overview.ru.html).

---

## trunkline — это

- **spec-driven development фреймворк** для AI-агентов и LLM-ассистентов: спека, схема данных и
  описание теста утверждаются человеком раньше, чем агент напишет хоть одну строку кода;
- пайплайн для **brownfield** — для кода, который у вас уже есть, а не для чистого листа;
- CLI, который разворачивает этот пайплайн в любом хосте AI-агента — **Claude Code**, **Cursor**,
  **Codex CLI** и похожих — через слэш-команды или обычный `AGENTS.md`;
- способ закрепить доменные правила именно вашей команды (конвенции схем, контракт ошибок, формат
  миграций) так, чтобы агент их **реально соблюдал**, а не угадывал по существующему коду;
- сквозная трассируемость требования от бизнес-правила до кода, теста и базы знаний, плюс
  машинная сверка, которая блокирует коммит при расхождении.

## Какую проблему решает trunkline

Большинство SDD-инструментов дают процесс, но не знают, как на самом деле работает ваша команда.
Без явного правила AI-агент пишет код по общим разумным умолчаниям — и регулярно промахивается
мимо конвенций, принятых именно в вашем проекте:

- **Деньги.** Агент по умолчанию напишет `price: 49.99` (float) — а у вас деньги это только целое
  число в копейках: `price_cents: 4999`. Округление float рано или поздно украдёт копейку.
- **Удаление.** Агент по умолчанию напишет `DELETE FROM orders WHERE id = ?` — а у вас удаление это
  `UPDATE orders SET deleted_at = now()`, и физического `DELETE` в кодовой базе нет вообще.
- **Ошибки.** Агент по умолчанию вернёт `{"message": "not found"}` — а у вас любая ошибка это
  `{"error": {"code": "ORDER_NOT_FOUND"}}` по общей схеме, и тело в принципе есть только у `2xx` и
  `400` — у остальных кодов его нет и не будет.
- **Время.** Агент по умолчанию напишет `datetime.utcnow()` — а у вас таймстемп обязан быть
  `timestamp(0)` в `Europe/Moscow`, а не в UTC.

Каждый такой промах по отдельности выглядит мелочью, но именно из них набирается ревью, которое
бракует код не за баг, а за то, что он не похож на остальной проект. Агент либо угадывает такие
правила по существующему коду (и регулярно промахивается), либо их объясняют заново в каждой
задаче. trunkline переворачивает это: доменные правила — часть процесса. Они живут в
сменном **профиле стека**, а стек-агностичное **ядро** ссылается на них по роли, а не пересказывает
заново. Расширили гайдлайн — пайплайн не изменился. Сменили стек — изменился профиль, а не ядро.

## Быстрый старт

Важная тонкость, которую часто упускают: **доступ к модели — это ещё не агент.** Токен к API
Claude, GPT и т.п. даёт только текстовый движок — он может *предложить* правку файла или команду,
но выполнить её сам не может. Чтобы агент реально читал и правил файлы, запускал сборку, тесты и
`git`, нужен отдельный **хост** — программа у вас на компьютере вроде
[Claude Code](https://claude.com/claude-code), Cursor или Codex CLI. trunkline устанавливается
именно в такой хост, а не «в модель».

Что нужно перед началом:

- установленный **Go** (см. версию в [`go.mod`](go.mod)) — чтобы собрать CLI из исходников;
- настроенный **агент-хост** с доступом к модели — по подписке (Claude Pro/Max и т.п., где хост уже
  встроен) или по API-ключу провайдера с оплатой по токенам;
- `git`.

Дальше — буквально три шага.

**1. Собрать и установить CLI** (один раз, из чекаута этого репозитория):

```bash
make install
```

Соберёт бинарь в свою папку и предложит добавить её в PATH. Откатить — `make uninstall`.

**2. Указать стек своего проекта:**

```bash
cd ваш-проект
trunkline init --profile oss-py-fastapi   # или example-stack — как шаблон под свой стек
trunkline doctor                           # проверяет, что всё поставилось верно, до прогона
```

`init` вендорит пайплайн в `.trunkline/`, добавляет блок флагов в ваш `AGENTS.md`, создаёт
`.pipeline/` и ставит commit-гейт. Обе команды безопасно перезапускать.

**3. Описать задачу — прямо в диалоге с агентом в вашем хосте:**

```
/trunkline-dev график автоплатежа не сохраняется, падает на пустом теле запроса
```

Правка, слишком маленькая для полного пайплайна (опечатка, guard-условие, строка лога), идёт по
отдельному короткому маршруту — те же правила профиля и тот же commit-гейт, но без лишних шагов:

```
/trunkline-quick сообщение об ошибке в обработчике платежа дублирует слово "оплата"
```

Нет слэш-команд в вашем хосте? Просто скажите агенту «следуй `.trunkline/AGENTS.md`» — этот файл
существует именно для того, чтобы у пайплайна была точка входа без каких-либо специальных функций
хоста. Команда не англоязычная? `--language ru` при `init` ставит русскую локализацию ядра.

Полная установка, все флаги и их значения по умолчанию — в [`SETUP.md`](SETUP.md).

## Чем отличается от других SDD-фреймворков

| | trunkline | Kiro | Spec Kit | BMAD | OpenSpec |
|---|---|---|---|---|---|
| Brownfield | **да, это целевой кейс** | нет | слабо | нет | да |
| Доменные правила вашей команды | **да, отдельный профиль под стек** | нет | нет | нет | нет |
| Смена стека | **меняется профиль, ядро не трогается** | н/д | н/д | н/д | н/д |
| Классификация задачи | **да, 6 маршрутов** | нет | нет | Quick mode | профили workflow |
| Покрытие цикла | **спека → прод → CI** | спека → код | спека → код | спека → код | спека → код |
| Блокирует на расхождении спеки/кода | **да, машиной (шаг 7a)** | частично | да (`analyze`) | да, через ревью | только структура |
| Накопление контекста между задачами | **да (`.pipeline/knowledge/`)** | нет | нет | нет | да |
| Трассируемость требование → код | **да, сквозная** | сильная (EARS) | средняя | сильная | средняя |
| Измеримость процесса | **да (журнал прогонов)** | нет | нет | нет | нет |
| Принуждение к правилам | текст + машинные гейты | **UI-структурное** | текст | текст | текст |
| Переносимость между агентами | средняя | средняя | **высокая** | высокая | высокая |

«Только структура» у OpenSpec — не пробел, а другая цель: его `verify` проверяет, что артефакты
изменения хорошо оформлены, а не что правило совпадает в спеке, схеме, тестах и коде одновременно.

Честно о слабостях trunkline: принуждение к правилам всё ещё во многом социальное — одно
«продолжай» не там, где нужно, и контракт сломан. Переносимость реальная, но неравномерная —
субагенты и хуки это фичи Claude Code, и без них ревью слабее. [`core/ORCHESTRATION.md`](core/ORCHESTRATION.md)
прямо говорит, что должен уметь хост, что опционально и что деградирует без каждой возможности —
ничего не деградирует молча.

## trunkline в цифрах

Архитектурно: **21** шаг пайплайна (грузятся по одному, не все сразу), **6** маршрутов по типу
задачи (bug / feature / refactor / migration / config-ci / audit / knowledge), **1** основной агент
(а не рой субагентов), **16** блокирующих гейтов `[STOP]`, где нужно явное «да» от человека.

---

## Четыре единицы работы

Запрос становится коммитом через четыре декомпозиции. У каждой свой владелец и свой лимит размера.

| Единица | Производит | Размер | В итоге становится |
|---|---|---|---|
| **эпик** (epic) | трекер — это вход | — | то, с чего начинается анализ |
| **задача** (task) | аналитик, шаг 4 | ≤ 24 рабочих часа | issue в Jira на Epic Link эпика |
| **ченджсет** (changeset) | разработчик, шаг 4 | одна вертикальная способность (capability), API до базы; после ~8 файлов план объясняет почему | один коммит |
| **инкремент** (increment) | разработчик, шаг 8 | ~100 строк | один `git add`, не коммит |

Читайте таблицу сверху вниз: аналитическая ветка (шаги аналитика) делит эпик на задачи; **одна**
задача попадает в ветку разработки — это и есть «задача», которую классифицирует шаг 0 — и делится
на ченджсеты; ченджсет пишется инкремент за инкрементом и становится одним коммитом на шаге 18.

Обе ветки режут **вертикально** — задача и ченджсет каждый раз это рабочая функциональность через
все слои, а не «сначала вся база, потом все хендлеры». Отличаются высота и читатель: задачу читает
человек в трекере, ченджсет — `git log`. Jira-специфика (`task`/`subtask`/`slice`) — в
[`SETUP.md`](SETUP.md).

## Маршруты

Шаг 0 классифицирует задачу и запускает только нужные шаги — баг не получает полную церемонию.

| Тип | Шаги |
|---|---|
| **bug** | 0? → 1 → 7(доказать) → 8 → 9+10 → 18 → 20 |
| **feature** | 0? → 1 → 2 → 3 → 4 → (5 → 6? → 7 → **7a** → 8 → 9+10 → 11 → 12 → 15 → 16? → 18)×N → 17 → 19? → 20 |
| **refactor** | 0? → 1 → 3 → 4 → (8 → 9+10 → 11 → 12 → 18)×N → 20 |
| **migration** | 0? → 1 → 2 → 3 → 6? → 7? → **7a?** → 8 → 9+10 → 18 → 20 |
| **config/ci** | 0? → 1 → 19 → 18 → 20 |
| **audit** | 1 → 7a? → 9+10 — ревью существующего кода, ничего не пишет |
| **knowledge** | 0? → 1 → 2 → **21** → 20 — сверяет базу знаний с кодом, не пишет код |

Это роли одного основного агента, а не 19 субагентов — порождение субагентов разрешено ровно в
трёх местах (параллельные Critic и Security, `Explore` для больших чтений, Agent Teams для 3+
конкурирующих гипотез). Везде ещё это запрещено — подробности в [`core/ORCHESTRATION.md`](core/ORCHESTRATION.md).

## CLI

| Команда | Что делает |
|---|---|
| `trunkline init` | Вендорит пайплайн, пишет блок флагов, создаёт `.pipeline/`, ставит гейт |
| `trunkline update` | Обновляет ядро и профили; гоняет миграции формата; сохраняет ваши правки |
| `trunkline doctor` | Проверяет всю установку — флаги, профиль, гейт, базу знаний, расхождение версий |
| `trunkline profile list/show/add` | Показывает и устанавливает профили стека |

Всё записанное фиксируется хешем содержимого в `.trunkline/state.yaml`, так что `update` отличает
свой вывод от ваших правок и никогда молча их не перезаписывает.

## Гайдлайны профиля

Доменные правила живут в профиле, и ядро обращается к ним по **роли** (`api_spec`, `data_types`,
`auth`, `migrations`…), никогда по имени файла — переименуйте файл или подставьте в тот же слот
другой документ, и в ядре ничего не изменится. Какие шаги читают какие роли и что с ними делают —
в [`profiles/README.md`](profiles/README.md) и [`core/README.md`](core/README.md).

## Структура

```
core/         пайплайн: маршруты, гейты, трассируемость, знания, телеметрия — стек-агностично
├── developer/    пайплайн разработки (21 шаг)
├── analytic/     пайплайн анализа (эпик → требования EARS → задачи Jira)
├── skills/       общее: база знаний по коду
├── l10n/         локализации, применяются как оверлеи поверх английского источника
└── ORCHESTRATION.md   что обязан уметь хост и что деградирует без этого
profiles/     профили стека: язык, команды, гайдлайны, надстройки шагов
publishers/   контракты издателей задач, которые может объявить профиль
internal/     CLI trunkline
evals/        тест-кейсы маршрутизации, по одному файлу на скилл
scripts/      гейты, прогоняемые перед коммитом
agent-skills/ submodule → addyosmani/agent-skills (только чтение)
```
